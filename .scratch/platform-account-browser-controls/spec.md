# 平台账号：独立打开专用浏览器与快速登录状态检查

Status: implemented
Labels: implemented

## Problem Statement

用户希望自行在专用浏览器中登录采集平台，然后让应用读取当前登录状态。现有“平台账号”页面以“一键检测”为主要入口，将启动浏览器、检查状态和等待用户登录绑定在一起。未登录时操作长时间占用，用户难以判断检查是否已经结束，也缺少明确的独立浏览器入口。

“专用谷歌浏览器暂时不可用，请重新检查；应用会在需要时自动启动。”没有说明此次操作发生了什么、用户下一步应该做什么，并把启动失败、窗口关闭和检查失败混为一谈。

## Solution

页面顶部以“打开专用浏览器”为主按钮，以“检查全部”为次按钮，替换原“一键检测”。各采集平台保留“检查状态／重新检查”。用户主动打开专用浏览器，在其中自行登录；检查操作只读取当前状态，发现未登录就结束，不等待扫码、确认或验证码。完成登录后，由用户重新检查更新状态。

打开浏览器与检查登录状态是两个独立动作。浏览器未打开时，检查提示用户先打开，不隐式启动登录流程。短暂的页面加载可以显示“检查中”，但不能演变为等待人工操作的长时间任务。

## User Stories

1. As an 应用使用者, I want a 明确的“打开专用浏览器”主按钮, so that 我可以主动开始登录。
2. As an 应用使用者, I want a 首次点击即可启动的专用 Chrome 窗口, so that 我无需配置日常浏览器。
3. As an 应用使用者, I want a 再次点击可回到已有窗口的入口, so that 我不会得到多个重复浏览器。
4. As an 应用使用者, I want a 保留当前页面的打开操作, so that 正在进行的扫码或验证码操作不被跳转打断。
5. As an 应用使用者, I want a 五个平台的登录入口, so that 我不必记忆各平台网址。
6. As an 应用使用者, I want a 自行完成平台登录的浏览器, so that 应用不必持续等待我的操作。
7. As an 应用使用者, I want a 与打开浏览器分离的“检查全部”按钮, so that 我能按需要刷新五个平台的登录状态。
8. As an 应用使用者, I want a 每个平台独立的状态检查入口, so that 我只刷新刚完成登录的平台。
9. As an 应用使用者, I want a 检查期间清晰的“检查中”反馈, so that 我知道操作已被接受。
10. As an 应用使用者, I want a 检测到未登录后立即结束的检查, so that 我不用等到登录或超时才能继续操作。
11. As an 应用使用者, I want a 登录完成后手动重新检查的流程, so that 更新时机由我决定。
12. As an 应用使用者, I want a 不因某个平台未登录而停止的全平台检查, so that 我能获得其余平台的状态。
13. As an 应用使用者, I want a 区分未登录与无法判断的结果, so that 网络故障不会被误认为账号退出。
14. As an 应用使用者, I want a 安全验证出现时结束并提示的检查, so that 我可以自行到浏览器处理。
15. As an 应用使用者, I want a 浏览器关闭后的明确提示, so that 我知道需要重新打开窗口。
16. As an 应用使用者, I want a 启动失败时具体且可重试的反馈, so that 我不用猜测“暂时不可用”的含义。
17. As an 应用使用者, I want a 防止重复点击创建重复操作的界面, so that 我不会无意启动多个检查或浏览器进程。
18. As an 应用使用者, I want a 显示最近检查时间的状态, so that 我知道页面记录是否可能已经过时。
19. As an 应用使用者, I want a 不因打开浏览器而改变登录结论的页面, so that 启动成功不会被误报为登录成功。
20. As an 应用使用者, I want a 保留专用浏览器已有登录态的升级, so that 我无需因为此次交互调整重新登录全部平台。
21. As an 正在采集的使用者, I want a 不抢占采集页面的账号检查, so that 我的采集进度不会被打断。
22. As an 处理暂停批次的使用者, I want a 完成登录后仍需显式继续的采集批次, so that 账号检查不会意外恢复采集。

## Implementation Decisions

- 修改平台账号页面、平台连接服务及其公共 API 契约，复用现有专用 Chrome 生命周期和浏览器操作协调器。不引入第二套浏览器运行时。
- 新增独立的“打开专用浏览器”服务操作与 API。它返回打开成功或明确的失败结果，不创建平台登录检查任务，不改变平台登录状态。前端只在操作进行时显示“打开中…”。
- 已有可用窗口时仅置前，不重置当前页面、不重复创建进程；没有窗口时启动或恢复项目专用窗口，沿用现有独立配置目录。首次窗口只显示空白标签页，五个平台首页由各平台行入口按需打开；已有窗口不强制返回起始页。
- 检查入口不自动启动已关闭的浏览器。没有可用专用窗口时直接提示打开浏览器，不将五个平台全部写为“未登录”。
- 复用现有按平台发起检查和读取状态的 API 入口；检查任务只执行有界页面加载与一次状态判定，不保留等待用户扫码或验证码的轮询阶段。异步接受与短时状态轮询可以保留，以免 HTTP 请求长期阻塞。
- 默认每个平台检查最多 20 秒，超时结束为“检查失败”，不等待原有数分钟的登录时限。五个平台串行检查总时长上限为 100 秒；浏览器关闭或后端不可用时提前结束剩余检查并明确说明。时间预算包含平台导航和状态判断。
- 平台账号的可见状态为“待检查、检查中、已登录、未登录、检查失败”。明确的登录页或未认证证据才判为“未登录”；明确认证证据才判为“已登录”。页面未加载、网络失败、无法识别或安全验证均不能强行判为未登录。
- 安全验证返回终态“检查失败”，附“请在专用浏览器中完成验证后重新检查。”；不在平台账号检查中保留“需要操作／等待操作”这一活跃状态。
- 状态检查完成后清除活跃检查标识，记录检查时间并释放协调器。失败、超时、取消和浏览器断开也必须释放，迟到结果不能覆盖后发检查。旧的等待操作状态不应在新页面中形成永久禁用按钮。
- “检查全部”按现有平台顺序检查微博、抖音、快手、小红书、今日头条。未登录或单个平台检查失败不阻止后续平台；每行独立显示结果，不把混合结果包装成“全部已登录”。
- 对会导航的检查使用现有操作互斥机制，避免与舆情爬取和内容补全争用。遇到占用时提示“专用浏览器正在执行任务，请稍后检查。”；单纯置前已有窗口不应跳转或中断任务。
- 检查使用临时检查页面或等效的独立页面，不导航用户正在登录的页面；结束后清理应用创建的检查页面，保留用户窗口与登录页面。页面内部通信正常工作，不恢复网络拦截、WebSocket 封锁或页面冻结。
- 五个平台的登录入口仅打开平台首页，不触发账号检查。登录由用户完成，应用不代填密码或验证码；平台返回与跳转正常加载。
- 错误提示按证据区分：启动失败用“专用浏览器打开失败，请重试。”；从未打开用“请先打开专用浏览器，再检查登录状态。”；已关闭用“专用浏览器已关闭，请打开后重新检查。”；未登录用“尚未登录，请在专用浏览器中登录后重新检查。”；加载或网络失败用“检查失败，请稍后重试。”。后端无法连接时用“无法连接本地服务，请确认服务已启动。”，不误报 Chrome 故障。
- 保留最近检查时间；关闭窗口不等于清除网站登录态。浏览器断开后的历史结果必须表现为需要重新检查，不能伪造新的未登录结论。
- 更新前后端状态及错误解析契约，并处理已有内存状态的兼容性；不为这次交互变化新增登录态数据库或迁移用户浏览器数据。
- ADR-0002 的“采集批次遇到人工障碍后整批暂停，用户显式继续”保持有效。本规格移除的是账号检查等待登录的行为，不是舆情爬取或内容补全的人工处理机制。账号检查成功不得自动继续批次。
- 所有服务、验证与浏览器均在用户本机运行，遵守项目 local-first 规则。

## Testing Decisions

- 优先复用平台账号页面与公共后端 API 的现有集成测试入口，只断言用户可观察的状态、提示、请求结果与重复操作行为；不通过函数调用次数或内部私有字段代替功能验证。
- 前端沿用现有应用级路由测试及平台连接 API 契约测试，覆盖主次按钮、独立打开、单平台与全部检查、未登录终态、检查失败分类、检查完成后的按钮恢复和最近检查时间。
- 后端沿用已有搜索流程中的平台连接 API 测试与可注入采集器，验证检查结束释放操作权、未登录不等待人工输入、单平台失败不阻断全部检查、占用冲突和迟到结果隔离。
- 只在现有浏览器生命周期测试入口补充必要验证：重复打开复用窗口、窗口关闭后再次打开、启动失败、保留登录页面、清理临时检查页和断开后的恢复。复用现有替身，不增加新的测试基础设施。
- 超时用可控时间或既有短预算配置验证，不让测试真的等待 20 或 100 秒。判定测试覆盖“未认证、已认证、验证码、页面未加载”四类可见证据，避免仅通过改状态字符串让测试通过。
- 本地实机验收五个平台：未登录检查能结束；用户自行登录后再次检查能识别；打开按钮不会打断当前登录页面；关闭并重新打开保留已有配置；检查不会恢复暂停采集。真实登录结果与替身测试结果分别记录，不以测试通过代替平台可用性证明。
- 人工账号登录和安全验证由用户完成；若某平台无法完成真实验收，记录具体未验证项，不声称五平台均通过。

## Out of Scope

- 本次只编写规格，不直接实施代码变更。
- 自动登录、自动完成验证码、登录状态后台持续监控、自动刷新或自动恢复采集。
- 新增采集平台、修改关键词采集策略、内容补全、报告生成或自动任务的业务规则。
- 重新设计整个平台账号页面、替换平台图标或引入新的设计系统。
- 接管日常 Chrome、复制日常浏览器凭证、迁移浏览器配置或使用 Centaurus。

## Further Notes

- 本规格承接用户对“打开专用浏览器＋检查全部”的讨论；第一版落实独立打开和短时检查，不再把用户登录视为一次检查任务的等待阶段。
- 五平台范围遵循 ADR-0010；浏览器发现与受控原帖获取的分工遵循 ADR-0003。此次改变不撤销这两个决策。
- 验证入口已向用户提出确认，目前按所提范围记录，可根据回复调整。20 秒单平台预算、首次窗口的空白标签页、平台行入口及临时检查页面属于为使交互可实施而明确的默认设计，不声称这些细节由用户逐项指定。
