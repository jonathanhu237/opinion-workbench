# 微博登录复用准备

Status: open
Type: research

结论：已记录用户的微博范围授权，但没有完成登录态迁移，也没有验证专用浏览器当前是否已登录微博。

## 本轮新增授权

- 用户预计离开一段时间，允许后续实现需要微博登录时复用本机 Chrome 中自己的微博登录态，并要求检查能否复制到项目专用 Profile。
- 授权只覆盖微博及本机项目专用浏览器，不包含其他网站账号、日常浏览历史、保存的密码或整个 Chrome Profile 的复制，也不允许把凭证发给第三方服务。
- 这是对先前“不读取日常浏览器登录态”默认边界的微博范围补充，不是取消浏览器工具限制、绕过保护措施或扩大平台访问范围的授权。
- 登录失效或遇到安全验证时，仍遵循暂停和用户显式继续规则，不能因用户离开而自动突破该边界。

## 已核查事实

- 应用代码已把浏览器数据目录作为配置传入浏览器工作器，并提供固定的项目专用目录。更换采集器本身不要求重建或清空该目录；是否已有有效登录尚未通过页面验证。
- 本机 Chrome 应用元数据显示版本为 152.0.7977.66。本轮仅读取应用版本及项目源码，没有检查个人 Profile 文件、Cookie、密码、会话存储或系统钥匙串。
- Chrome 浏览器连接可用，但当前公开工具能力没有会话导出、导入或 Profile 迁移接口；Chrome 技能也限制直接读取 Cookie、Profile 和会话存储。本轮没有借其他工具绕过这些限制。
- Chrome 官方说明，自 136 起不能用远程调试开关调试默认数据目录，要求使用非默认目录，并强调隔离日常 Profile。不能把给日常浏览器加调试参数当作已经可用的会话迁移方案；这也不等于证明所有迁移方式在技术上都绝不可能。[Chrome 官方说明](https://developer.chrome.com/blog/remote-debugging-port?hl=en)
- Chrome 用户数据目录包含历史、书签、Cookie 等多类信息，复制整个目录会超出仅复用微博登录态的范围。[Chromium 用户数据目录说明](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md)

## 后续实现应遵循的处理

1. 优先复用项目固定的专用浏览器目录，不因替换 MediaCrawler 而清空登录态或每次新建临时 Profile。
2. 将登录准备与采集验收分开。登录状态必须通过对应浏览器中的可见微博页面确认，不能从文件存在或浏览器已启动推断登录成功。
3. 若没有受支持且范围可控的迁移方法，请用户在项目专用 Chrome 中正常登录一次；以后复用该目录，但不保证会话永不过期。
4. 后续如提出新的迁移实现，应先说明能否严格限定微博、是否会改动原浏览器、如何保护凭证，以及工具是否允许该操作。不得复制整个日常 Profile、输出 Cookie 或擅自读取系统密钥。
5. 在登录准备未完成时继续允许离线代码开发和隔离回归，但不能把微博实机验收标为完成，也不能因此开始小红书试验或自动化改造。

## 本轮实际动作

只进行了源码、应用版本、浏览器公开能力及官方文档核查，并补充相关任务说明。没有打开微博页面、读取或复制凭证、创建或改动 Profile，也没有执行采集或开始实现 tickets。
