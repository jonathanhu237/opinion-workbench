# 采集层重设计讨论地图

Status: open

## 当前收敛结论

- 2026-09-03 实施进度：用户已明确授权 implement。01–13 离线实现及回归已完成，14 等待受控微博实机范围确认；无真实账号/付费模型访问，旧采集器默认与用户 fork 保留。当前验证和风险以 `implementation.md` 为准，下文“尚未授权实现”等说明仅属于当时的讨论历史。

- Q24.1、Q28 已确认：手动采集只负责入库；报告界面从内容库手选条目或一键选取未分析条目，开始后自动完成补全、总结和报告，并复用选中条目的可用成功总结。
- 采集到报告的一键编排归自动化，本轮不考虑其设计或实现；此前 Q18 的手动默认流程由 ADR 0008 取代，ADR 0004 保留历史并标为 superseded。
- 首批只验证微博；全库失败选择、显式人工恢复、部分条目失败后报告、媒体清理及未适配平台过渡等已确认规则不变。
- 已按用户明确调用的 `to-spec` 将 `spec.md` 整理并发布为正式规格，状态为 open、标签为 ready-for-agent；包含用户故事、实现决策、测试决策及范围边界。具体组件和工程参数的验证列为实施事项，不标为已实施或已验收。
- 下文保留历轮讨论的原建议和当时状态；与上述最新结论冲突的操作描述仅供追溯，不再作为当前手动流程要求。

## Notes

- 本文记录 `grill-with-docs` 访谈过程，不是实施规格或已批准的架构决策。
- 用户正在评估自研采集层以及最终移除 MediaCrawler 的方向；已确认微博先行及受控混合方式，具体工具、迁移方法和验收标准尚待讨论。
- 当前仅允许调研与设计文档工作；在用户确认整体理解一致前，不实施迁移或修改应用代码。
- 最新 Q28 已明确手动选材启动与自动化编排的归属，不再存在 Q18 与 Q24 的待确认冲突；设计范围以 ADR 0008 为准，尚未授权实现。
- 已安排只读核查产品实际采集能力、进程协议及替换边界；不启动浏览器、使用账号或发起采集。
- 已有代码表明采集方式是混合的；“使用真实浏览器”与“所有采集都由网页操作驱动”不能混为一谈。
- 自研是否改善可维护性，与是否降低平台风控，是需要分别验证的假设。
- 本地子模块的 origin 为 `https://github.com/jonathanhu237/MediaCrawler.git`；后续判断以用户维护的 fork（含工作区改动）和产品实际接入为准，不只看上游说明。
- 用户补充的主要痛点：反复提示页面结构变化、运行不稳定，以及为适配产品维护大量改动。
- 用户在第四轮答复前要求先讨论更上层的产品链路：搜索并保存 URL → 补全文字/图片/视频 → 单条 LLM 内容总结 → 聚合结果生成报告；随后明确一次点击“开始分析”自动运行“舆情爬取”和“报告生成”两个阶段，显示进度，直接交付报告及条目分析状态，不需要中间确认。此操作边界已确认，仍不等于授权实施迁移；Q12–Q17 不因这一答复自动得到确认。

## Verified facts

- 产品当前开放微博、抖音、快手、小红书、今日头条，已有搜索及正文/媒体补全框架，但不代表每个平台的正文、图片、视频都已完整可用；产品 worker 协议和数据模型尚未接入评论采集。上游其他平台或评论能力不自动计入当前产品的迁移基线。
- 当前边界是产品服务通过受控常驻子进程调用产品专用适配器；独立进程有固定启动路径和严格消息协议，并非只替换一个搜索函数。
- 已有恢复依据主要是已完成关键词的连续前缀，不是任意页面游标；替换时需要明确兼容或迁移这种语义。
- 现存少量运行记录不足以归因用户历史上的不稳定，也不足以建立稳定性基线。
- 依据：`third_party/MediaCrawler/tools/auth_worker.py`、`backend/src/longtian_api/services/media_crawler_auth_worker.py`、`backend/src/longtian_api/search_checkpoints.py`。
- 用户 fork 已包含五平台产品专用搜索/补全、常驻 worker、消息协议、媒体校验及人工恢复等能力，不能仅视为上游入口的薄封装。
- 提交 `8a7b620` 修复头条搜索结果延迟加载导致的结构变化判定；提交 `c56d375` 修复已完成搜索仅含站外卡片时的结构变化判定。两者都不是单纯 DOM 改版：前者是时序，后者是结果分类。依据：`third_party/MediaCrawler/media_platform/toutiao/client.py:246`、`:307` 及本地提交补丁。
- 当前抖音未提交改动将结构变化进一步区分为页面状态、搜索上下文、搜索响应、搜索结果和分页不兼容；这些已有改动需保留，不能当作本轮访谈的实施成果。依据：`third_party/MediaCrawler/media_platform/douyin/product_search.py:240`。
- 当前跨平台批次串行；非成功状态会暂停整个批次并保留浏览器占用。人工验证不会自动恢复，用户点击继续后按已完成关键词恢复，也可跳过当前平台；重启后不自动启动采集。依据：`backend/src/longtian_api/repositories/search_batches.py:370`、`backend/src/longtian_api/services/search_batches.py:497`。
- 两轮只读核查均已完成；没有启动服务或采集，没有修改用户 fork。
- 微博当前正文补全从页面投影正文和图片候选，未证明完整的视频清单；长文本可能只标注为部分内容。默认媒体下载许可列表中微博条目为空，worker 使用默认配置，因此获取图片候选不等于实际完成图片下载。依据：`third_party/MediaCrawler/media_platform/weibo/product_enrichment.py:48`、`third_party/MediaCrawler/tools/product_media.py:38`、`:319`、`third_party/MediaCrawler/tools/auth_worker.py:527`。这是前述“已接入媒体补全”的重要范围修正。
- 当前补全流程已在代码层面分开内容投影与文件下载，且包含文件大小、媒体类型、哈希、来源地址等检查；接入第三方下载器需要重新核对这些约束，不能视为命令行替换即可完成。
- 下载器公开源码核查已完成，详见 `downloader-research.md`：gallery-dl 是微博帖子级内容提取候选，yt-dlp 主要适合视频；小红书也有支持“链接 → 正文/媒体”的 XHS-Downloader。但这些工具会自行请求平台，可能有 Cookie、隐式会话与重试行为，并非单纯搬运已获得的文件；没有使用任何账号实测，候选不等于已选型。
- 配置/凭证/媒体生命周期核查完成，详见 `runtime-contract-research.md`：默认运行库当前保存 20 个组合搜索词，自动任务配置每词 3 条、每 60 分钟、五平台但已停用。单次无中断微博搜索最多输出 60 条，不代表请求量或媒体下载量；结果输出上限、执行预算与安全/时效承诺必须分开。
- 微博当前在本地 worker 内使用从专用浏览器取得的对应域 Cookie 发 HTTP 搜索请求；给新第三方组件使用登录态依然需要确定信任边界。未读取任何凭证内容。
- 当前媒体只在分析补全时暂存，逐条分析结束便清理，历史记录只有正文、媒体元信息与分析输出；媒体期限/容量管理需要新增持久缓存。现有分析结果复用不能等同于原始媒体文件复用。
- 两阶段产品讨论的代码核查：当前导航区分手工采集、结果与分析、自动任务等入口，结果页面还可独立发起和重试初步分析；自动工作流已串联 `collection → initial_analysis → topic_report`，但手动初步分析不自动生成报告。正文/媒体补全已经是单条分析内部步骤。依据：`frontend/src/app/shell.tsx:95`、`frontend/src/routes/results.tsx:254`、`frontend/src/routes/results-jobs.tsx:310`、`backend/src/longtian_api/services/automation_workflows.py:781`、`backend/src/longtian_api/services/content_analyses.py:299`。
- 当前单条模型输出不只是自由文本摘要，还包括地点线索、时间背景、媒体观察及不确定性；输入证据、缺口和来源等另行保存，主题相关性判断属于报告阶段。两阶段产品分组不意味着丢弃这些已有信息或把相关性判断前移。依据：`backend/src/longtian_api/schemas/content_analyses.py:57`、`backend/src/longtian_api/schemas/topic_reports.py:357`。
- 去重核查：现有搜索结果按全库 `(platform, platform_content_id)` 识别同一内容，另记录每次 `new/repeated` 命中；微博从内容 ID 构造统一详情 URL，但不是任意外部 URL 的通用归一化器。内容身份、访问 URL 和是否成功分析是三件事。依据：`backend/src/longtian_api/repositories/search_runs.py:306`、`third_party/MediaCrawler/media_platform/weibo/product_search.py:125`。
- 当前同一自动任务仅将首次登记的内容加入分析集合，后续再次发现并不会因之前分析失败而自然重新入选；已有显式重试/重新分析入口。这是“曾发现就永久跳过”的实际语义风险，而不是假想问题。依据：`backend/src/longtian_api/repositories/automation_workflows.py:1011`、`backend/src/longtian_api/repositories/content_analyses.py:356`、`:445`。
- 部分失败核查：单条分析队列可在部分条目失败后完成并推进报告；但搜索和内容补全的登录/验证阻断处理目前不一致，补全阶段可能退回摘要继续。模型配置缺失可阻断任务，实际 HTTP 鉴权失败却可能只记单条失败后继续。已接受的人工暂停原则需要在新链路统一落实，不能声称现有实现已完全满足。依据：`backend/src/longtian_api/services/content_analyses.py:211`、`:256`、`:304`、`:386`、`backend/src/longtian_api/services/automation_workflows.py:1050`、`:1208`。
- 报告目前区分“无可用来源”和“无相关来源”，二者不生成正常正文；报告判断/汇总节点失败也不会发布为完整成功报告。来源条目失败不等于报告自身生成失败。依据：`backend/src/longtian_api/services/topic_reports.py:201`、`:299`、`:308`、`:334`。
- 状态建模核查：内容主记录、每次单条分析尝试、任务成员和报告成员已经分离。同一内容可以有多次分析尝试，也能被多份报告引用；某份报告生成失败不能成为内容本身唯一的全局失败状态。依据：`backend/src/longtian_api/database.py:1418`、`backend/src/longtian_api/migrations/initial_analysis.py:58`、`backend/src/longtian_api/migrations/automation_workflows.py:128`、`backend/src/longtian_api/migrations/topic_reports.py:46`。
- 现有 `new/retry/reanalysis` 相关选择能力有复用基础，但尚无用户提出的“仅新增 / 新增加失败项”组合策略。报告重试已有独立记录边界：复制原成员与分析证据到关联的新报告，不在该方法里重新采集或进行单条分析。依据：`backend/src/longtian_api/repositories/content_analyses.py:356`、`backend/src/longtian_api/repositories/topic_reports.py:1014`。

- 实施进展：已完成 [01](issues/01-collector-boundary-prefactor.md)、[03](issues/03-selected-summaries-to-report.md)、[04](issues/04-stored-text-to-report.md)、[05](issues/05-library-wide-pending-and-failed.md)、[09](issues/09-partial-failure-and-report-retry.md)。详细测试与脏工作区基线记录见 implementation.md；02 已领取，尚无真实账号验收或旧库删除。

- 不采购第三方数据或付费采集服务。来源：用户明确约束。
- 运行保持本地优先，浏览器相关流程在用户本机进行。来源：项目 `AGENTS.md`。
- Q1 已确认：优先可靠获取所需数据、减少人工介入、失败可恢复，其次控制维护成本；风控改善独立验证，具体数值目标待范围和负载明确。
- Q2 已确认：正常采集自动进行；遇到登录、安全验证等问题提示用户处理，处理后继续。Q6、Q7 进一步明确了显式恢复与批次暂停边界；具体状态验证方法待后续设计。
- Q3 已确认：只服务当前项目，不做通用采集平台。已记录到 `docs/adr/0001-project-scoped-collection.md`。
- Q4 已确认：首批替换微博，不先替换小红书；用户明确担心试验损伤小红书账号。小红书不作为新采集层试验对象，不因下载器调研启动任何小红书访问。
- Q5 已确认：第一版需要搜索结果、正文、图片、视频，不采集评论。用户提出发现内容 URL 后委托维护中的开源下载器获取信息，作为待评估架构方向，尚未选定工具或授权接入。
- Q6 已确认：用户完成人工处理后自行点击继续采集，不自动恢复。
- Q7 已确认：等待人工处理时先暂停同批次其他平台；只使用已有数据的分析不应被整体停用。Q6、Q7 的取舍记录到 `docs/adr/0002-explicit-resume-after-manual-action.md`。
- Q8 已确认：接受浏览器发现链接、可替换的第三方组件解析指定内容和下载媒体的受控混合方式，不要求全部访问都由浏览器页面操作完成。应用保留请求与任务控制权；具体工具、凭证边界仍未选定。记录到 `docs/adr/0003-controlled-hybrid-collection.md`。
- Q9 已确认：正文或媒体不齐全时，保留部分采集结果并允许用于明确标注缺口的分析；按正文、图片、视频分别表达完整性，不以部分结果冒充完整成功。平台登录或安全验证仍遵循整批暂停。
- Q10 已确认：正文随记录保留，媒体有期限和空间上限，重复分析优先复用；用户要求后台提供媒体保留策略设置。具体默认值、清理顺序和历史分析引用的处理仍需确定，不是立即清理现有文件的授权。
- Q11 已确认负载来源：实际负载依据项目已有配置，不额外要求用户重新报一组关键词/数量/频率；只读配置核查已完成。配置上限不等于时效承诺或安全配额，验收目标待补全范围等决策确定后讨论。
- 用户在 Q19 明确以移除 MediaCrawler 为目标，接受先单平台验证再逐个平台适配；具体移除时点与过渡兼容策略仍未决定。任何特定下载器尚未选型。
- Q18 历史决定（已由 Q28 / ADR 0008 取代）：当时约定一次“开始分析”自动完成舆情爬取与报告生成，记录到 ADR 0004；用户现已明确该全链路编排属于自动化，不是本轮手动默认流程。
- 原有登录/安全验证时暂停、用户点击继续的异常处理规则仍有效。正常阶段切换不需要人为确认，与异常后的显式恢复不是同一件事。
- 用户再次认可一次启动、两阶段进度、最终报告及条目分析状态，并要求继续讨论，指出任务可能变复杂。下一轮先明确完整链路的首批交付范围和业务行为，不把“继续讨论”解释为开始实现。
- Q19 已答复：可以先只做一个平台，再以共同接入边界适配其他平台；结合已确认 Q4，首个平台是微博。单平台先行与最终退出 MediaCrawler 的方向写入 `docs/adr/0005-single-platform-first-migration.md`；不承诺后续平台零适配，也不自动执行删除旧库。
- Q20、Q22 已答复增量原则：用户希望按内容链接去重，不对重复条目默认反复调用模型。Q21.2 进一步明确历史失败项是否处理应由选项控制，而不是更改新增/重复分类。现有平台内容身份去重可作为实现基础；旧结果是否参加本次报告仍未明确，用户没有确认按有效期自动重新分析。
- Q21 / Q21.1 已确认：个别帖子失败时标记条目失败及原因，继续处理其余内容，用可用分析结果生成报告并说明覆盖缺口。该确认不改变登录/安全验证时暂停的规则，也不代表报告汇总自身失败可以标记成功；失败条目后续重试与报告步骤恢复仍需确定。
- Q21.2 已确认并纠正助手原建议：再次搜到已发现 URL 仍按重复命中；是否处理历史失败项由分析选项决定，例如仅新增，以及新增并包含失败项。不得将失败项重新标为新增，也不默认因再次命中就自动重试。该边界记录到 `docs/adr/0006-discovery-and-processing-policy.md`；具体选项名称、默认值与范围尚未固定。
- Q21.3 已确认：报告失败后保留已完成成果，由用户重试报告，不重新搜索、下载或逐条分析。用户据此提出为条目定义状态；条目与报告的状态归属、展示名称仍在讨论，不把其举例的串行状态链直接视为已批准模型。
- Q23 已确认并纠正助手误解：爬取只负责发现、去重、入库；后续分析面向数据库中的积累内容，选择包含失败项时应涵盖全库当前失败项，不以是否在本次搜索再次命中作为条件。助手原先“仅本次命中失败项”的建议已被明确否定，已修正 ADR 0006 和领域术语。
- 两阶段通过持久内容库衔接，不是第一阶段产生一个本次 URL 列表并把它当作第二阶段全部候选；本次没有新增 URL 也不等于数据库没有可处理内容。业务候选范围与实际执行所需的平台能力/安全暂停规则分开，不把能力限制悄悄改写成“只处理本次命中”。
- 用户认可数据库衔接边界后询问是否还有其他需要讨论。本轮收拢为报告选材、原媒体保留、第三方组件登录态和旧平台过渡四个有实际取舍的边界；常规实现细节在方案中提出默认设计，不继续逐字段访谈。
- Q24 已明确报告选材：采集数据入库后，在报告生成界面选中想分析的数据，或一键分析所有未分析数据；选中数据自动进入总结到报告的处理。Q24.1 随后确认复用选中条目的已有成功总结，不自动加入未选中的历史内容。
- Q28 已确认独立操作边界：手动采集入库与报告选材启动分开，报告生成内部自动完成补全、总结和汇总；采集到报告的一键编排交给自动化，用户明确要求本轮先不考虑。已更新领域术语与 ADR 0008，并移除 ADR 0006 中旧的一键手动流程表述。
- Q25 已确认：即使已被报告引用，原图/视频也可按保留策略清理，正文、总结、报告和来源记录仍保留；记录到 ADR 0007，本轮未删除媒体。
- Q26 已确认：如果补全需要登录态，则可使用本项目对应平台的必要登录态；已补入 ADR 0003，具体组件及凭证传递方法仍需审查，没有开展任何凭证提取或平台访问。
- Q27 已确认：微博新流程验收并移除旧依赖后，尚未适配的平台可以暂时停用新采集，保留历史数据与报告查看能力；已补入 ADR 0005，不表示当前立即删除 MediaCrawler。
- 术语明确后按需更新根目录 `CONTEXT.md`；其中只写项目领域术语，不放技术实现或讨论草稿。
- 架构决策满足难以逆转、有真实取舍、未来需要解释原因时，再按需记录到 `docs/adr/`。

## Round 1

### Q1：成功标准

问题：第一版“更优”最优先解决什么，什么结果值得替换现有采集器？

建议：优先验证任务结果可靠、失败可定位可恢复、适配维护负担可控；平台风控变化单独测量，不预先承诺自研会减少风控。具体数值目标在采集范围和负载明确后确定。

答案：用户认可建议，并说明当前主要痛点是频繁提示页面结构变化、运行不稳定，以及为适配产品维护了很多改动；要求检查其自行维护的 MediaCrawler。优先级已确认，数值验收标准仍待后续讨论。

### Q2：人工参与边界

问题：用户启动一批采集任务离开电脑后，系统应该独立完成到哪一步，什么时候可以要求用户回来处理？

建议：正常搜索、翻页、读取内容和入库自动完成；登录、安全验证和无法安全恢复的异常允许暂停并请求人工处理。正常采集不要求用户逐页操作。

答案：用户确认遇到登录、安全验证等问题应提示其处理，然后继续。恢复触发方式和暂停影响范围尚未确认。

### Q3：产品边界

问题：第一版采集器需要被哪些产品或使用者调用？

建议：先只服务本地舆情应用，保持清晰可替换的内部边界；暂不承担通用采集平台、外部用户接口或分布式运行需求。

答案：用户明确只服务本项目，不做通用采集平台。

## Round 2

### Q4：首批替换范围

问题：第一批希望替换哪些平台？

建议：先替换小红书，其他四个平台暂时保持可用；用真实产品任务验证新采集层后，再按平台逐步迁移。

答案：用户否定小红书先行，明确要求首批替换微博，原因是担心试验导致小红书账号封禁。小红书不作为试验平台。

### Q5：数据能力边界

问题：第一版新采集层必须交付哪些数据能力，是否保持当前产品边界？

建议：先对齐搜索结果、正文、图片/视频获取，不在重构时同步扩展评论采集。评论若为必需，应明确作为新增能力进入范围，而不是误以为产品已经支持。

答案：用户确认先不采集评论，先获取搜索结果、正文、图片和视频；提出发现 URL 后交由 GitHub 上维护中的下载器获取信息。该委托边界与具体工具需进一步调研和决策。

### Q6：人工处理后的恢复

问题：用户完成登录或安全验证后，如何触发继续采集？

建议：由用户点击继续，再做一次有界状态确认并从已保存进度恢复；暂不靠后台持续探测登录/验证状态自动恢复。检查点粒度待后续决定，不预先承诺可在任意页面原位续跑。

答案：用户确认必须自行点击继续采集。

### Q7：暂停影响范围

问题：小红书等待用户处理时，同批次其他平台任务应该怎么办？

建议：第一版暂停当前采集批次并保留进度，避免自动操作与人工处理争用共享浏览器；已有数据的分析不应因此被整体停用。是否需要跨平台继续采集由用户确认。

答案：用户确认等待人工处理期间先暂停其他平台。

## Round 3

### Q8：第三方内容解析与下载的边界

问题：是否接受由自有浏览器采集层发现内容链接，再通过可替换的开源组件解析指定内容并下载文件，即使组件内部仍调用平台接口？

建议：接受经过能力和行为审查的混合实现；自有层保留任务范围、登录/验证处理、请求预算、结果校验和入库的控制权。候选工具、凭证传递方式、隐式请求及错误映射尚未选定或授权。

补充：优先核验 gallery-dl 的微博单帖提取是否满足契约，必要时才增加视频辅助组件。如果接入需要长期大幅修改下载器内部，或其请求/暂停行为无法受控，则不因其现有能力而强行采用。

答案：用户接受。混合方式已确定，具体工具、凭证使用及错误映射并未因此自动确定。

### Q9：部分内容的交付

问题：正文已获取但某张图片或视频失败时，是否保留并允许使用已获得的部分内容？

建议：按正文、图片、视频分别记录完整性，保存成功部分并清楚列出缺失；已获得的信息可用于明确标注缺口的分析，不把部分结果标记为完整成功。登录或安全验证仍遵循整批暂停，区别于单个文件缺失。

答案：用户确认可以使用部分采集结果开展分析，按建议清楚标注缺失。

### Q10：内容保留

问题：采到的正文、图片、视频需要保留多久，是否需要在后续分析时复用？

建议：以本地可复用的采集快照为方向，避免每次分析重新访问平台；媒体采用可配置期限和空间上限，不默认永久保存全部视频。具体期限、空间及删除语义待确认。

答案：用户接受建议，并要求在后台提供期限和容量管理选项。具体默认值及自动清理对历史分析的影响尚待讨论。

### Q11：微博试点规模与时效

问题：首批微博试点期望每次有多少关键词、每词多少条结果、每天运行多少次，以及多久完成可接受？

建议：先以少量关键词、小批次、单账号串行验证稳定性；数量与耗时作为待用户确定的验收输入，不视为平台安全配额。

答案：用户说明实际负载应由现有配置决定。转为只读核查当前关键词、数量、调度和执行限制，不重复要求用户报告代码中可查的事实；配置驱动已确认，时效和稳定性验收目标仍未确定。

问题：指定的本地解析组件需要登录时，是否允许它使用当前微博连接的必要登录态？

建议：允许仅本任务、仅对应平台的受控使用，不读取日常浏览器或其他平台登录态，不写普通日志或命令行参数，不向外部服务交付。具体接口是否需要临时凭证文件需审查，不预先承诺绝不落盘；本轮只讨论授权边界，不实际提取凭证。

答案：待用户确认。

### Q14：普通失败后的兜底

问题：组件遇到普通解析或下载失败后，是否应自动换另一工具或访问方式继续尝试？

建议：第一版不自动串联多个工具或整帖多轮访问；仅对确认可重试的暂时故障做有界重试，仍失败则记录具体原因与部分结果，供用户主动重试。登录、安全验证和无法确定访问状态时停止请求，按已确认规则进入待人工处理。

答案：待用户确认。

### Q15：恢复的进度粒度

问题：是否要求继续采集时保留已发现链接及各帖正文、媒体的完成进度，而不是只按完成的关键词恢复？

建议：保存已发现内容队列与已成功获取的项目，恢复优先处理未完成部分；成功且仍有效的内容/文件不重复获取。不承诺动态搜索页能够精确原位恢复，确需重访时仍去重并受请求预算约束。

答案：待用户确认。

### Q16：媒体到期和容量清理

问题：媒体达到期限或容量上限后，是否允许自动清理旧媒体，同时保留正文和历史分析记录？

建议：优先清理到期文件，再按较久未使用顺序腾出空间；正在使用的文件不得清理，无法腾出空间时停止新增媒体下载并说明原因。保存正文、来源、采集时间、媒体哈希和历史分析，单独标明本地媒体已清理，不把历史获取成功改写成失败。具体期限/容量默认值在设置方案中提出，不在此执行任何删除。

答案：待用户确认。

### Q17：已清理媒体的重新获取

问题：再次分析时发现媒体已清理，重新下载是否需要使用者明确触发？

建议：默认只使用现有内容并说明缺失，不因再次分析就自动访问平台；提供明确的重新获取操作。新获取的内容记录新的获取时间，不覆盖旧分析使用的内容记录。这与 Q12 的首次补全不同。

答案：待用户确认。

## 两阶段产品模型讨论

用户提议并进一步确认：搜索并保存 URL → URL 补全文字、图片和视频（如有）→ LLM 产出单条内容总结 → 聚合结果交给 LLM 生成报告；第一步为“舆情爬取”，后三步为“报告生成”。主要动因是现有应用把操作拆得过细；两个阶段只是一次完整分析中的进度分组，不是让用户分别启动的两个任务。

已确认的用户体验：一次点击开始分析，正常流程自动运行并展示当前阶段/进度，最后直接呈现报告以及每条内容的分析状态。中间不要求查看结果后再点击生成报告。

助手判断与建议（尚非完整实施规格）：

- 支持两个对用户可见的业务阶段，不要求用户为报告依次发起和管理多个技术任务；配置和故障详情可以展开，但不应成为必经步骤。
- 舆情爬取输出应是可追溯的搜索结果清单，除 URL 外保留当时可取得的平台内容标识、标题/摘要、来源和采集时间等最小信息；不能宣称这时正文和媒体已全部取得。
- 报告生成自动衔接指定结果的内容补全、单条内容理解和报告汇总。各步骤内部仍有进度和已完成成果，不能合成不可恢复的一次性黑盒；报告汇总失败不应自动导致重新搜索、下载或逐条调用模型。
- 单条产物不应只剩脱离来源的自由文本摘要；至少保留关键事实、来源关联和缺失说明，便于报告回溯证据，并避免重复素材被误当成多个独立事件。
- 报告生成阶段中的内容补全仍会访问平台，因此同样适用登录/验证时暂停并由用户继续的原则。现有 ADR 的意图应保留，具体跨阶段状态映射待模型确定后设计。
- 这次只评估工作流分组；页面合并、任务对象迁移、旧数据兼容、删除路由等均未授权实施。

### Q18：两个阶段的衔接

问题：舆情爬取完成后，报告生成如何启动？

原建议（已被用户否定）：手动流程提供明确的生成报告入口，可查看采集范围后启动；定时任务按配置自动串联两阶段，不要求用户在中间确认。后一阶段内部自动完成补全、单条理解和汇总，不增加三次操作。

答案：用户明确不需要中间确认；点击开始分析后显示当前阶段和进度，两个阶段自动运行到底，直接给报告并提示哪些条目已被分析。

说明：这不是要求隐藏运行状态，也不是授权取消安全验证时的人工暂停。主界面只需两个阶段，详细动作和条目状态可作为进度说明；具体状态标签、复用条目如何计数、是否进入报告与已分析之间的关系待设计，不冒充已确认需求。

## Round 5：控制改造范围与确定报告行为

背景：用户已认可两阶段一键分析模型，并担心整体工作变复杂。本轮只讨论有产品影响的选择；一般实现细节由实施方案提出，不逐个转交用户决定。

### 复杂度判断与开发建议（未授权实施）

- 当前涉及三个改造面：统一任务入口/进度和最终交付，微博搜索与受控内容获取，以及持久媒体缓存与容量/期限管理。
- 优先复用现有单条内容分析、报告汇总、配置、历史数据和自动工作流基础；复用不等于保证无须改动接口，也不把本轮变成全项目重写。
- 建议按可验证的内部工作项拆解，但对用户始终保持一次启动、两个阶段。开发上的分步交付不能重新变成产品中的多次手动操作。
- 首批完整微博链路要同时验证正常完成、普通条目失败、登录/验证暂停与显式继续；这些验证在设计确认后开展，不在当前账号上启动试验。
- 历史数据默认保留并兼容查看，不自动回填媒体、批量重新调用模型或删除旧记录。额外回填属于另一个需明确授权的范围。

### Q19：新完整流程的首批范围

问题：新增的一键分析完整流程是否也先只在微博上打通？

建议：首批微博贯穿搜索、内容补全、单条理解、报告和条目状态；其他平台暂保留原实现与已有可用路径，小红书不参与试验。共有配置和历史记录继续保留；微博验证达标后再讨论其他平台接入与旧入口清理。

答案：用户表示既然要去掉原采集库，可以先只做某一个平台，跑通后再适配其他所有平台。结合 Q4，首个平台仍为微博；共享工作流可以复用，平台细节仍需独立验证。其他平台在过渡期是否保留旧运行路径、旧依赖何时物理移除，不能仅凭此答复预设。

### Q20：自动分析的条目范围

问题：按现有配置搜出的结果，去重后是否全部自动进入本次补全和分析？

建议：本次配置范围内去重后的条目都进入处理，不增加人工筛选或隐藏的相关性前置过滤；无法补全或分析的条目单独记原因。单条已分析不等于一定被报告正文引用，主题相关性和归纳仍属于报告阶段。此问题接续 Q12，但不再假设中间由用户选择下一阶段。

答案：用户提出 URL 唯一，可以按 URL 去重，只让非重复内容进入分析。已确认不重复分析的意图；代码事实显示应区分同一内容身份、链接别名及分析完成状态。失败后再次发现和旧分析参与报告的规则需另行澄清。

### Q21：部分条目失败时的报告交付

问题：部分条目无法完成分析时，是否继续用可用的分析结果生成报告？

建议：有可用分析时继续汇总，并明确本次搜索、已分析、部分内容分析、未分析的覆盖情况与原因；全部无可用分析时不给出伪装为成功的内容报告，而是说明无可用材料。登录、安全验证仍先暂停等待用户继续，不归入自动跳过的普通单条失败。

答案：用户先要求单独讨论，随后在 Q21.1 明确同意：个别帖子失败标记出来，再用剩下的内容分析。普通条目失败的处理已确认，其他类型故障并未一并确定。

### Q22：重复命中的复用

问题：同一条内容再次被搜索到时，是否允许复用有效期内的内容和单条分析结果？

建议：允许在来源、有效期及相关分析配置符合条件时复用，报告仍按本次范围重新汇总，条目状态区分本次新分析与复用既有分析。不能仅因 URL 相同就宣称内容未变；来源变更的可观察性、有效期和刷新规则在此方向确认后具体设计。

答案：用户要求见 Q20，即仅非重复内容进入分析。不能据此记录为同意按有效期自动重采重分析；媒体的保留期限与单条分析的重复执行是不同规则。

## Q21 单独讨论：按失败影响范围区分

用户明确要求将失败行为单独讨论，本轮不再同时铺开全部待决问题。

已确认前提：正文/媒体不齐全仍允许标注缺口后分析（Q9）；遇平台登录/安全验证暂停并由用户显式继续（Q2、Q6、Q7）。这两条不能替代对“整条没有分析结果”或“报告自身失败”的判断。

### Q21.1：零散来源不可用

场景：本次去重后有 20 条需要分析的内容，其中 2 条已删除或明确无法读取，其余 18 条成功；没有遇到账号登录/安全验证或模型服务全局故障。这是设计示例，不是实际运行数据。

问题：是否自动用这 18 条生成报告，并标明另外 2 条未分析及原因？

建议：允许这种覆盖不完整但可追溯的报告，同时保留未完成条目的处理记录，不把它们标成已分析；未成功条目如何后续补做另行确定。不据这个答案自动推出“任何失败比例都可以报告”或“报告汇总本身失败也算成功”。

答案：用户确认可以，个别帖子失败应标记为失败，再用其余内容进行分析。既有对报告覆盖缺口的说明建议一并保留，失败条目不能显示成成功分析。

### Q21.2：失败条目再次命中

场景：某条帖子上次因暂时故障分析失败，下次搜索又发现同一内容；如果仅按“URL 已出现过”跳过，就仍没有该帖的分析结果。

问题：失败条目再次被搜到时，是否允许补做，而不是当成已分析的重复条目永久跳过？

原建议（用户改为策略可选）：成功过的默认不重复分析；暂时性失败下次命中时可以有限补做，确认已删除或当前不支持的内容不自动反复请求。设置重试上限并保留失败记录；具体次数与故障分类属于后续实现方案，不将该问题变成无限自动重试授权。

答案：用户明确搜索只发现 URL，再次发现仍算重复；失败可能发生在后续任意环节。应提供处理选项，例如仅分析新增且包含失败、仅分析新增且不包含失败，由选择决定是否补做，而不是见到历史失败就默认重试。

### Q21.3：最终报告失败后的恢复

场景：内容获取及单条分析已完成，但最后报告判断/汇总没有成功交付。

问题：是否保留已完成成果，由用户点击重试报告，仅继续报告生成内部未完成的报告步骤？

建议：保留已有单条分析和可复用的报告步骤结果，不重新搜索、不重新下载、不重复逐条分析。显示报告失败及原因，用户明确重试后再调用必要的模型步骤；不能把尚未交付的报告标成成功。

答案：用户接受，并提出是否应给每个条目定义待总结、总结失败、待生成报告、生成报告失败等状态。用户确认了独立恢复原则，但状态归属和枚举尚待共同确定。

## 条目处理策略与状态建模

### 已确认的边界

- 新增/重复描述搜索发现，处理成功/失败描述后续执行，二者不能互相改写。
- 开始分析时应有包含/不包含失败项的策略；它是启动配置，不是在两个阶段之间增加一次手动操作。
- 报告失败只重试报告，成功的单条总结和已取得的有效内容不因报告失败作废。

### 助手建议（状态方案草案，未实施）

- 选项文案建议为“仅处理新增”和“处理新增并重试失败项”，避免把历史失败叫作新增；先不自动扩展为重新分析全部历史等额外模式。
- 发现记录保留本次新增/重复分类。每次入选条目的处理记录保留待处理、处理中、已总结、失败等简要状态，并另外说明当前环节或失败环节（内容补全、单条总结等）。
- 原文/图片/视频的完整性单独记录：允许分析的不完整素材可以得到“已总结，但内容不完整”，不把每个媒体缺失都升级成条目失败。
- 每份报告单独有待生成、生成中、已完成、失败等产出状态。报告阶段的判断/汇总进度可作为详情，不再增加顶层业务阶段。
- 条目与报告通过本次成员关系相连，能够显示该条目在某份报告中的处理情况；不能用一个全局字段声称条目永久处于“生成报告失败”。例如同一条目的总结已成功，报告 A 成功而报告 B 失败，两者应同时表达。
- 失败是相应步骤的异常分支，不是所有条目必须经过的线性阶段；重试创建或保留可追溯的执行记录，不覆盖前一次成功结果。
- 当前已有独立尝试、报告成员及重试记录，可以优先复用；这些草案不等于决定重建全部表或删掉历史记录。

### Q23：失败项的处理范围

问题：选择包含失败项时，是否只重试本次搜索命中的历史失败条目？

原建议（已被用户否定）：首版限制在本次搜索范围内，不自动扫描和补做全库失败记录；若以后需要历史失败专项处理，再明确范围和触发方式。本次只是决定候选范围，平台访问仍遵守登录/验证暂停与有界请求原则。

答案：用户明确爬取的职责只是把信息获取后存入数据库，后续分析是另一个阶段；选择包含失败项，应涵盖所有数据中的失败项，不限于本次搜索命中的记录。助手此前混淆了采集范围和分析候选范围。

### Q23 后的数据边界修正

- 第一阶段向持久舆情内容库写入、去重；第二阶段从内容库依据处理策略查询候选，不依赖本次搜索结果列表作为唯一入口。
- 包含失败项意味着纳入全库当前仍失败的条目；早期尝试失败、后来已经成功的条目，不因历史里曾有失败就自动再次当成失败项。
- 示例：库中有 200 条已成功分析、10 条历史失败，本次新增 5 条；选择新增并包含失败项时，应处理这 5 条及库中 10 条失败项，不要求后者这次再次被搜到。数字仅为设计示例。
- 即使本次新增为零，第二阶段仍应依据数据库候选工作，不能仅因爬取没有新增而直接认定无事可做。
- 本次明确的是全库失败范围；分析选项“新增”的完整定义需与“搜索新增命中”分开，尤其要考虑此前已入库但尚未处理的记录。暂不把仅限当前采集批次的条件重新引入该定义。
- 本轮当时沿用的一次开始、两阶段自动衔接已由后续 Q28 修正：手动报告从内容库选材启动，全链路编排归自动化且暂不考虑；内容库的持久数据边界没有改变。
- 全库候选是业务语义；首批只实现微博时，对尚无适配能力的平台条目须明确呈现能力限制，不启动未经授权的小红书试验，也不声称已经支持所有平台。

### 其余待后续展开的场景

- 已成功分析的重复命中是否只跳过单条处理，还是也不计入本次报告；增量模型调用与报告覆盖范围是两个决定。
- 模型鉴权/配置等系统性故障如何暂停，以及普通暂时故障的有界重试规则。
- 全部来源不可用、全部不相关时，交付何种状态；没有可用材料不能编造报告正文。

## 收敛轮：其他需要明确的边界

用户已认可数据库驱动的两阶段模型，本轮目的是结束不必要的细节发散，同时保留真正影响行为、访问权限和数据保留的选择。

### Q24：报告使用哪些已有总结

问题：新的报告是否可以使用库中以前已经总结成功的内容，而不仅是本次新总结的条目？

建议：允许报告按自身主题和选材范围使用库中已有总结，避免重复单条分析；报告引用和覆盖范围应可追溯。报告选择范围与“哪些内容需要重新处理”是两个规则，不因此自动重新抓取旧条目，也不默认把全库所有总结无差别塞入一份报告。

代码事实：当前自动报告按本次分析任务的 `job_id` 冻结来源（`backend/src/longtian_api/repositories/topic_reports.py:863`）；独立报告已有按内容首次发现时间范围读取历史记录、优先复用匹配的成功分析的能力，缺少分析时记录缺口而非自动补做（同文件 `:950`）。现有报告配置通过提示词表达主题，并提供首次发现时间范围；没有独立结构化主题或平台筛选参数（`backend/src/longtian_api/schemas/topic_reports.py:134`、`frontend/src/routes/results-report-actions.tsx:293`）。旧实现能力和限制不作为新业务约束，尤其不能把首次发现时间误称为帖子发布时间。

答案：用户明确采集入库后，应在报告生成界面选中想分析的数据，或有一键分析所有未分析数据的按钮；这些数据进入总结到报告的处理模式。原问题中“历史总结”经 Q24.1 的具体选材例子解释后，已确认仅复用选中条目的可用总结；Q28 也已确认手动与自动化的操作边界。

### Q25：被报告引用的原媒体能否清理

问题：已经生成报告的条目，其原图/视频是否也允许按照媒体保留策略自动清理？

建议：允许清理原媒体缓存，但保留正文、单条总结、报告、来源和当时处理记录；清理后明确原媒体已不在本地，不保证仍能回看原图/视频。此处确认的是证据保留取舍，不执行删除；若需要永久保留原始证据，则须另设明确保留规则。

答案：用户确认可以清理。保留正文、总结、报告、来源和处理记录，清理后不保证原媒体可回看；此处确定保留政策，不执行实际文件清理。

### Q26：本地组件使用登录态

问题：是否允许经过审查、明确选定的本地解析/下载组件使用本项目对应平台的必要登录态？

建议：允许限定组件和任务范围内使用，只取得当前平台必要信息，不向第三方数据服务交付、不读取其他平台或日常浏览器的登录态。不得写入普通日志或命令行参数；具体工具如需要临时凭证文件须单独审查，不承诺所有实现都能完全不落盘。当前只讨论设计边界，不提取任何凭证。

答案：用户确认，如果需要登录态才能补全，则可以使用登录态。按已讨论边界仅使用本项目对应平台的必要信息，不扩大为读取日常浏览器或其他平台凭证；具体组件、传递方式和行为控制仍需审核。

### Q27：未适配平台的过渡期

问题：微博新流程验证通过并移除 MediaCrawler 时，尚未接入新实现的平台是否可以暂时显示未适配、不可执行新采集？

建议：允许。保留历史数据和已生成报告的查看能力，逐个平台适配后恢复新采集；未支持能力要明确展示，不把它伪装成无结果，也不自动触发旧库或旧平台账号访问。实际移除旧依赖仍在设计确认和微博验收之后执行，本轮不删库或代码。

答案：用户确认可以。微博新流程验收并移除旧依赖后，未适配平台暂时不可新采集，保留历史数据和报告查看能力，逐一适配验收后恢复；本轮没有实施切换或删除旧库。

### Q24.1：选中条目已有总结时的处理

问题：手动选中 10 条，其中 3 条已经有可复用的成功总结，是否直接复用这 3 条、只总结另外 7 条，再用选中的这 10 条生成报告？

建议：允许。未被选中的旧内容不自动加入；一键分析未分析条目时，也不因为历史条目已有总结就擅自扩大选材范围。数字只是解释场景，不增加默认强制重分析。

答案：用户确认没有问题。选中 10 条中若 3 条已有可用总结，则复用这 3 条，只处理另外 7 条，再以选中的 10 条作为本份报告的来源候选；复用不扩大选材范围，也不等于重新调用单条模型。

### Q28：采集与报告的操作衔接

问题：是否以“先采集入库，随后在报告生成界面选数据并点击开始，自动完成总结到报告”替代之前“一次开始自动完成采集与报告，中间无需选材操作”的正常流程？

建议：按本轮最新描述明确为采集入库与选材生成报告两个操作边界，报告生成内部自动完成补全、总结和汇总，显示进度并交付报告；不自行额外保留两套工作流。若用户只想增加一个历史数据选材入口，则需保留旧默认流程并明确这个新增入口的地位，不能由助手默认为其中一种。

答案：用户确认理解正确，并明确“一次开始自动完成爬取和报告”应交给自动化部分，本轮先不考虑。手动采集与报告选材启动分开，补全到总结到汇总内部自动衔接；ADR 0004 已由 ADR 0008 取代，未修改或运行现有自动化。

### 交给实施方案的默认设计（尚未批准实施）

- 手动采集与报告选材启动分开；报告生成内部自动完成内容补全、总结和汇总，技术步骤、失败环节与报告成员状态独立记录，不成为额外必经页面或人工确认。自动化编排明确排除在本轮范围之外。
- 处理选项按内容库状态表述；“本次搜索新增命中”与“库中待处理”严格区分。默认是否包含失败项在方案中明确列出，不默认为所有任务无限自动重试。
- 为一次执行保存明确候选集合与已完成成果，避免任务运行期间数据变化导致进度总量无限增长或重试重复处理成功项。
- 模型配置/鉴权等明确的全局障碍不能逐条重复调用；没有可用材料时不编造报告正文。没有相关材料与执行失败应分别表达。
- URL 规范化、内容身份、凭证保护、媒体校验、可取消/恢复、有界请求与重试是实现要求，不再逐个询问低层参数。
- 验收覆盖配置驱动的新数据处理、全库失败选取、部分条目失败报告、验证暂停/继续、报告单独重试、媒体清理和历史数据可读；外部试验仅在明确范围内，不能预先承诺新方案消除风控。
