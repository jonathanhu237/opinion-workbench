# Windows 与 macOS 便携 ZIP 及 GitHub Release 发布

## Problem Statement

使用者希望直接从 GitHub Releases 下载解压即用的舆情系统，不需要安装器、macOS .app、源码或自行配置构建工具。当前已有 Windows ZIP 构建脚本，但数据位于系统用户目录；尚无 macOS 便携入口及双平台自动发布流程。

使用者已确认 Windows x64 和 Mac Apple Silicon 各一个 ZIP，运行依赖随包提供，数据跟随解压文件夹保存，升级时保留数据。两个平台不能共用同一套二进制。

## Solution

提供两个独立的带版本 ZIP：Windows 解压后双击 EXE；macOS 解压后双击“启动.command”，不交付 .app。入口启动包内服务并在普通浏览器打开界面，用户无需安装 Python、Node 或开发工具；采集仍需本机 Google Chrome。

数据放在解压目录内独立的数据文件夹，程序资源与可写资料分离。发行包不包含任何已有用户数据，首次启动创建空白业务库。升级先完全退出、备份并保留数据，再使用新版程序。

推送版本标签后，GitHub Actions 分别在 Windows x64 与 macOS arm64 原生环境构建、检查最终 ZIP，成功后上传到同一版本的 Release 草稿，由维护者确认后公开。初期不做安装器和自动更新。

## User Stories

1. As a Windows 使用者, I want 从 Release 下载 Windows x64 ZIP, so that 无需自行构建程序。
2. As a Mac 使用者, I want 下载明确标注 Apple Silicon 的 ZIP, so that 不会选错架构。
3. As a 使用者, I want 解压即用, so that 不经过安装向导或申请管理员权限。
4. As a Windows 使用者, I want 双击 EXE 打开本地网页, so that 不必手动启动前后端。
5. As a Mac 使用者, I want 双击“启动.command”打开本地网页, so that 不需要 .app 或输入命令。
6. As a 使用者, I want 包内包含运行依赖, so that 不必安装 Python、Node、包管理器或开发工具。
7. As a 使用者, I want 静态界面与 API 由同一本地服务提供, so that 不依赖开发服务器或源码目录。
8. As a 使用者, I want Chrome 缺失时得到明确提示, so that 知道采集所需的外部依赖。
9. As a 使用者, I want 缺少 Chrome 时仍能查看历史和配置, so that 不被阻断全部功能。
10. As a 使用者, I want 数据存放在解压目录的独立文件夹, so that 知道业务资料的位置。
11. As a 使用者, I want 重开后保留内容库、单条总结、报告记录和舆情报告, so that 可以持续工作。
12. As a 使用者, I want 平台访问间隔和总结并发偏好也保留, so that 便携交付不丢失配置。
13. As a 使用者, I want 同机移动整个目录后仍可使用资料, so that 路径变化不会产生另一套空白数据。
14. As a 使用者, I want 从中文和空格目录正常启动, so that 不必改变日常命名方式。
15. As a 使用者, I want 从不同工作目录启动仍使用同一数据位置, so that 快捷方式或终端入口不会分裂资料。
16. As a 使用者, I want 只读目录或缺失资源时看到可操作错误, so that 不面对无反应的启动入口。
17. As a 使用者, I want 同一数据目录重复启动不产生两个服务, so that 避免数据库和浏览器冲突。
18. As a 使用者, I want 有清楚的保留数据升级说明, so that 不会误删历史工作。
19. As a 使用者, I want 升级失败或版本不兼容时安全停止, so that 应用不会删库重建。
20. As a 旧 Windows 使用者, I want 有从系统用户数据目录迁入便携目录的说明, so that 不必重新建立业务资料。
21. As a 使用者, I want 凭据继续安全保存, so that 便携不意味着明文分发密钥。
22. As a 使用者, I want 知道跨电脑复制可能需要重新配置密钥和登录, so that 不误解系统凭据保护。
23. As a 使用者, I want 知道使用后的数据目录包含敏感信息, so that 不把它整包分享给别人。
24. As a 使用者, I want 获得未签名程序的安全提示说明, so that 不把系统拦截误认成应用崩溃。
25. As a 使用者, I want 刷新和多页面操作继续沿用现有生命周期, so that 新包装不会误停工作。
26. As a 使用者, I want 关闭最后一个应用页面后正常退出, so that 不留下长期后台服务。
27. As a 使用者, I want 重开后中断任务不自动执行, so that 仍由我决定何时重新发起。
28. As a 维护者, I want 版本标签触发原生双平台构建, so that 不用手动在两台机器打包。
29. As a 维护者, I want 锁定依赖并记录版本和源提交, so that 可以复现和排查发行问题。
30. As a 维护者, I want 对最终解压包进行启动检查, so that 构建成功不被误当成运行成功。
31. As a 维护者, I want 两个平台通过后才形成 Release 草稿, so that 不会悄悄发布残缺版本。
32. As a 维护者, I want 人工确认草稿后再公开, so that CI 不直接代替验收决定。
33. As a 下载者, I want 文件名标注版本、系统、架构并提供校验值, so that 能选对包并核对完整性。
34. As a 维护者, I want 重跑不覆盖已发布资产或混合不同提交, so that 发行历史稳定可追溯。
35. As a 维护者, I want 发行包排除个人数据库、密钥、登录态和日志, so that 不泄漏业务与账号资料。
36. As a 维护者, I want 构建失败保留诊断且不影响已发布版本, so that 可以安全修复和重试。

## Implementation Decisions

### 产物与原生构建

- 本版支持 Windows x64 和 macOS arm64（Apple Silicon），分别发布完整目录 ZIP；Windows 沿用当前 Windows 10/11 x64 边界。macOS 最低版本须根据实际固定工具链与部署目标明确记录，不承诺所有 macOS 都支持。
- Windows 复用现有冻结程序、静态前端和辅助进程的打包方向。macOS 增加原生 arm64 冻结产物及 .command 入口，脚本调用包内二进制，不调用用户系统 Python 或 Node，不生成 .app。
- 共用资源清单、应用 launcher 与包检查逻辑，避免复制两套业务服务。ZIP 保留 macOS 执行权限，所有资源通过包内相对位置解析；正确处理中文、空格和不同工作目录。
- 运行依赖随包提供，Chrome 是明确外部依赖，不额外下载另一套 Chromium。模型与平台访问仍需要网络及用户配置，“免安装”不等于完全离线。
- 不以构建机的环境、源码、虚拟环境路径或系统解释器补足包内缺失依赖；辅助获取进程也必须从发行包运行。

### 数据根目录与兼容

- 发行入口显式绑定解压目录下独立数据文件夹，复用现有数据根目录注入能力；程序资源、冻结器内部目录和临时解包目录不作为数据根目录。开发模式保留原有源码运行数据路径。
- 便携发行默认不写入 Windows LOCALAPPDATA 或 macOS Application Support。目录不可写时明确失败并提示更换解压位置，不静默切换到另一套数据位置。
- 数据包括 SQLite、配置、凭据、专用 Chrome profile、日志和必要实例记录。已退出的媒体缓存不因打包恢复。正常业务资料、限速设置和并发偏好必须跨重启及同机移动保留。
- 目前总结并发偏好使用浏览器 localStorage；实施时须处理本地端口变化导致 origin 变化的情况，优先沿用后端本地配置体系承载便携偏好，必要时做有限兼容迁移，不复制日常浏览器资料。
- 同机移动后不得依赖原解压目录的绝对路径而失效。共享同一数据目录的重复启动沿用既有单实例锁；拒绝并发占用数据库或专用浏览器资料，不增加多版本同时运行能力。
- 现有 Windows DPAPI 保护与 macOS 凭据权限校验继续保留；普通 API 和日志不回显密钥，不因便携改为不受保护的明文导出。
- 文件夹便携不保证密钥和登录态跨 Windows 用户、跨电脑或跨系统可用。无法解密时提示重新配置；平台登录失效时提示重新登录，保留业务数据。不增加跨 OS 凭据转换能力。
- 升级说明采用“完全退出、备份旧数据、新版解压到新目录、复制保留的数据到新版对应位置、验证后自行处理旧目录”。不要复制仍在写入的 SQLite；不在脚本里自动删除旧数据。
- 旧 Windows 用户目录到便携目录提供一次性手工迁移说明：同一用户下退出应用、备份、复制资料、启动新版。不得静默扫描或导入开发者、其他用户及日常浏览器资料。
- 数据库继续使用现有迁移链；失败或版本不兼容时安全停止，不删库重建，不承诺升级后的库可以直接降级打开。新发行 ZIP 不携带已初始化的个人业务库。

### 启动与安全提示

- 两个平台都复用本地 launcher、健康检查、静态资源服务和普通浏览器 UI，只监听本机回环地址；不引入桌面壳、托盘或长期后台服务。
- 保留现有多页面租约、刷新处理、最后页面关闭后约 10 秒停止退出、重复启动和端口占用提示。macOS 命令窗口如何退出需要明确说明，不因启动脚本结束留下不受控服务。
- 平台登录或安全验证后的显式继续、应用重开后中断任务不自动运行的规则保持不变。Windows 上此前“已中断”的原因尚未证明，本规格不声称重新打包就解决根因。
- 明确未签名、未公证发行可能受到系统提示或拦截。仅提供系统正规、针对具体程序的授权说明，不要求全局关闭 Gatekeeper、SmartScreen 等安全机制；临时签名不冒称可信发布签名或公证。

### GitHub Actions 与 Release

- 版本标签触发构建，建议采用 v 前缀语义版本。分别使用原生 Windows x64 与 macOS arm64 runner，显式验证架构；不能把 x64 二进制改名为 arm64 交付。
- CI 只负责构建及离线验证，不承载真实平台采集、登录或付费模型调用。这是本次明确授权的云端构建，不改变应用业务的 local-first 运行方式。
- 构建使用锁定依赖和固定工具版本，从干净 checkout 获取必要受版本控制资源／子模块，通过白名单在干净输出目录组装。用户机器无需安装 CI 工具链。
- 两个 ZIP 文件名包含版本、系统与架构；同时提供 SHA-256 校验值和简短使用说明，记录同一源提交。说明 GitHub 自动生成的源码 ZIP 不是可执行成品。
- 每个平台对最终 ZIP 的解压副本通过检查后上传中间产物；发布作业依赖两个平台成功并校验资产集合，创建或更新同标签 Release 草稿，不自动公开、移动标签或覆盖已公开版本。
- 同标签并发构建应协调，重跑仅能受控替换相同提交的草稿资产；任一平台失败不能生成伪完整发布。构建错误须留可读诊断。
- 权限最小化：构建只读仓库，Release 写权限仅给发布作业。不需要生产 API key、平台 Cookie、开发者数据或它们的 CI secrets。
- 发行内容审计排除个人数据库、密钥、浏览器 profile、报告、会话、日志及开发环境。烟雾测试在解压副本写入数据，不重新压回发行资产；不能压缩运行过的应用目录作为干净包。

## Testing Decisions

- 建议最高测试边界为最终 ZIP 解压后的真实启动入口：Windows EXE 和 macOS .command。复用现有健康检查、生命周期租约、临时数据目录和外部依赖替身，不另建桌面测试壳。
- 好测试验证实际可运行、静态资源与 API 可达、只监听本机、数据位于便携目录、重开保留和关闭退出；ZIP 存在、构建命令成功或脚本字符串匹配不能替代运行验收。
- 这些测试边界是基于代码提出的建议；本轮按不继续访谈要求发布，不冒称用户已逐项确认测试机制。
- 复用现有应用路径、launcher 生命周期、Windows 交付契约、凭据、Chrome 生命周期、报告取消及迁移测试，扩展为双平台成品验证。
- 两个平台分别原生构建并解压验证，覆盖中文／空格目录、不同 cwd、缺少资源、只读目录、端口占用和重复启动。macOS 额外验证执行位、shell 引用及正确架构。
- 隔离开发 PATH 和源码，确保没有 Python、Node、pnpm、uv 仍可运行，辅助进程从包内启动。CI 可用无自动打开浏览器模式及健康检查进行烟雾验证，但 Finder／Explorer 双击和系统隔离提示需实际验证并分别记录。
- 验证首次创建空白业务库、没有写入系统旧默认数据目录；保存合成内容、报告、配置、并发与限速偏好，重开、改变启动 cwd、同机移动后仍保留。
- 使用上一版合成数据覆盖保留数据升级和旧 Windows 用户目录迁移；升级失败不删库，旧目录不被脚本删除。运行中复制数据不作为合法升级流程测试。
- 在各系统验证凭据可读取和损坏／不兼容凭据的错误路径；不得在发行资产或测试日志泄漏密钥。跨用户复制不被标为保证成功。
- 验证刷新、多页、关闭最后页面、取消、重开中断任务和专用浏览器所有权，包装变化不得产生新的自动恢复或重复请求。
- 工作流测试覆盖单平台失败、资产缺失、版本混合、架构不符、校验值不符、同标签重跑、已发布版本防覆盖和权限分离。
- 最终 ZIP 进行敏感资料及资源完整性审计；烟雾测试前后原始发行资产散列不变。真实平台访问、付费 API 和目标机器实网验收需另行授权，不把假响应或 Mac 结果当成 Windows 实网通过。

## Out of Scope

- 一个 ZIP 跨系统运行、Intel Mac、Windows arm64、Linux、Universal Binary。
- macOS .app／DMG／PKG、Windows 安装器、商店发布、自动更新或开机启动。
- 购买签名证书、Developer ID 公证、关闭系统安全策略。
- 无提示自动迁移、跨设备同步／云备份、跨 OS 数据和凭据转换、保证跨机登录态有效。
- 云端真实采集和报告分析、第三方数据服务、Centaurus 验证。
- 更改舆情业务语义、恢复媒体缓存或多模态能力。
- 本轮实现、提交推送、创建标签、执行工作流或上传公开 Release。

## Further Notes

- 本规格替代旧 Windows 交付规格中的三项范围决定：安装器作为主要用户成品、固定系统用户数据目录、排除云端 CI 构建。生命周期、凭据安全和业务边界保持不变；云端授权只覆盖构建与离线验证。
- 旧 Windows 规格与当前 Windows 使用说明、路径实现反映旧方案，实施时必须同步更新，避免互相矛盾的升级说明。
- 已确认双平台 ZIP、便携数据目录与 Release 草稿发布。macOS 最低版本、GitHub 原生 runner 可用性和计费仍需实施时核实；不可静默替换架构。
- 配套已完成的总结并发及平台访问间隔功能应进入新发行包，不改变其已确认产品契约。重新打包不代表 Windows 中断问题已查明。
- 相关规格：[旧 Windows 交付](../windows-delivery/spec.md)、[单条总结并发](../report-summary-concurrency/spec.md)、[平台访问间隔](../platform-access-pacing/spec.md)。
- `ready-for-agent` 表示可领取，尚未生成双平台可下载成品；本轮仅发布规格。
