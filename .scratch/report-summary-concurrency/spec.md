# 生成报告时可配置单条总结并发数

## Problem Statement

使用者一次采集可能得到 216 条内容。当前报告生成内部按条串行执行内容补全、文字理解和单条总结保存：上一条模型请求完成后才处理下一条。模型等待时间与后续补全不能重叠，正文已经就绪的条目也无法并发总结，造成明显等待。

使用者希望在生成报告时选择并发数，首次默认 8，并记住上次选择；这不是同时生成多份舆情报告，也不是同时访问多个平台页面。

## Solution

在生成报告确认界面增加“单条总结并发数”，提供 1、2、4、8、16 五档，首次默认 8，之后使用上次提交的选择。本次请求一旦形成不可变提交意图，其并发设置即固定。

内容补全保持串行，并继续遵守既有平台访问预算、浏览器所有权和人工暂停恢复规则。正文就绪后进入有界队列，由最多所选数量的模型请求并发执行文字理解、形成单条总结。补全下一条与总结已就绪条目可以重叠；已有可用正文不必等待其他条目补全完成才总结，已有可用总结则按既有规则复用。

成功结果及时保存，进度按实际条目状态更新；所有选中条目完成必要处理、没有在途请求或待重试工作后，才进入报告汇总。正常按所选上限运行，仅在明确限流时退避、有限重试并向使用者提示。不承诺固定倍数提速。

## User Stories

1. As a 使用者, I want 在生成报告确认界面设置单条总结并发数, so that 我能控制批量内容的处理速度。
2. As a 首次使用者, I want 并发数默认是 8, so that 不需要研究参数也能避免大量内容逐条等待。
3. As a 使用者, I want 从 1、2、4、8、16 中选择, so that 可以根据模型服务能力调整处理规模。
4. As a 使用者, I want 应用记住上次提交的并发选择, so that 每次生成报告不必重复设置。
5. As a 使用者, I want 关闭并重新打开应用后仍保留偏好, so that 该设置不是仅在当前弹窗有效。
6. As a 使用者, I want 取消确认弹窗不改变已保存偏好, so that 临时试选不会影响下次任务。
7. As a 使用者, I want 看清该设置只控制单条总结, so that 不误以为会同时生成多份报告或打开多个平台页面。
8. As a 使用者, I want 216 条内容按有界并发处理, so that 能缩短模型等待而不一次发出 216 个请求。
9. As a 使用者, I want 正文已就绪的内容及时进入总结, so that 不被其他内容的补全阻塞。
10. As a 使用者, I want 下一条内容补全与已有正文的总结重叠执行, so that 两种等待不再完全相加。
11. As a 使用者, I want 平台内容补全仍保持串行和原有访问节奏, so that 不因总结提速而增加平台访问压力。
12. As a 使用者, I want 已有可用单条总结被复用, so that 不为并发改造重复支付分析费用。
13. As a 使用者, I want 只处理本次报告选材, so that 并发队列不会带入未选中的历史内容或后来采集的内容。
14. As a 使用者, I want 每条成功结果及时保存, so that 不必等全部完成才保住已完成工作。
15. As a 使用者, I want 乱序完成的总结仍对应正确来源, so that 报告不会错配帖子、作者或引用。
16. As a 使用者, I want 进度准确区分正在处理和已完成条目, so that 同时处理多条时也能判断进展。
17. As a 使用者, I want 个别条目失败不影响其他可处理内容, so that 一条异常不会阻断整批。
18. As a 使用者, I want 所有条目处理结算后才开始报告汇总, so that 不会遗漏较慢的总结。
19. As a 使用者, I want 平台登录或安全验证暂停时已有正文仍能继续总结, so that 平台障碍不会浪费已经完成的补全工作。
20. As a 使用者, I want 完成人工处理后显式继续才恢复内容补全, so that 应用不会擅自恢复平台操作。
21. As a 使用者, I want 没有明确限流时正常按所选并发上限运行, so that 不被无依据地降速。
22. As a 使用者, I want 明确限流时自动等待、有限重试并显示原因, so that 短暂服务限制不会立即造成整批失败。
23. As a 使用者, I want 重试有次数和等待预算上限, so that 不会无限等待或持续产生费用。
24. As a 使用者, I want 普通超时或结果不明确时不盲目重发请求, so that 降低重复调用和重复费用风险。
25. As a 使用者, I want 取消能停止新请求并清理在途工作, so that 点击取消后不会继续派发整批内容。
26. As a 使用者, I want 取消、故障或应用重启后保留已保存的总结, so that 后续明确发起时可以复用已有成果。
27. As a 使用者, I want 重复提交同一个请求不会重复创建任务或改变并发数, so that 网络异常时可以安全确认原请求结果。
28. As a 使用者, I want 任务启动后使用固定并发设置, so that 后续偏好变化不影响正在运行或排队的任务。
29. As a 使用者, I want 模型凭证或配置故障仍明确阻断受影响任务, so that 不会被当作普通条目失败持续发出无效请求。
30. As a 报告读者, I want 原帖文字不足的条目仍按既有规则列为待人工核查条目, so that 并发提速不会把缺失信息写成已确认事实。

## Implementation Decisions

### 范围与既有行为

- 本次改造手动生成报告内部的单条总结阶段，不改变报告选材、内容库去重、总结可复用性或报告汇总语义。
- 自动任务及独立分析入口的产品配置不在本次范围；共享执行器改造必须兼容这些入口，未显式配置的非手动任务维持原有串行语义，避免意外将调用量提高到 8。
- 内容理解仍限定原帖文字，不接入模型直接访问原帖 URL，不恢复媒体分析或媒体缓存。

### 确认界面、偏好与请求契约

- 修改报告生成确认交互、前后端创建请求校验、报告记录投影和持久化任务快照，增加单条总结并发数。
- 建议使用明确的 API 字段 `summary_concurrency`，严格接受整数集合 1、2、4、8、16；拒绝布尔值、浮点值、字符串、零、负数和其他整数。非法请求不得创建任务或调用模型。
- 新手动创建请求省略该字段时默认为 8；新界面始终显式提交选值。历史已存在任务保留历史串行语义，不把历史任务伪装成曾按 8 并发运行。
- 并发数属于不可变请求意图及后台任务快照，而非执行时读取的全局偏好。它必须随请求 UUID、选材与提示词快照一起保存，并参与幂等请求一致性判断。
- 相同 UUID、相同意图重放返回原任务；相同 UUID 修改并发数必须冲突，不能启动另一组请求。兼容旧版本缺少字段的历史请求重放，按其历史快照解释，不因新默认值导致重复执行。
- 本地持久化最近一次正式提交的选择；关闭弹窗不更新偏好。缺失、损坏或非法偏好回退到 8；偏好存储故障不应使有效报告请求失效。跨设备同步不在范围内。
- 网络结果不明确、恢复待确认请求时，优先显示并使用已保存意图的并发数，不读取更新后的偏好覆盖它。
- 确认界面简要说明“同时进行的单条总结数量；内容补全仍逐条执行”。任务记录可读出本次并发上限；运行中不提供修改入口。

### 有界执行与所有权

- 将当前串行执行器中耦合的内容补全与模型分析拆成串行补全生产端、有界就绪队列和并发总结消费端；不为所有 216 条一次创建无界模型请求。
- 复用现有 AI 配置操作租约：一个活动分析任务持有稳定配置，内部并发请求共享该配置快照。不要为每个 worker 重新竞争互斥配置租约，也不要为实现并发解除任务之间、报告阶段之间的既有互斥边界。
- 同一时刻该任务实际在途单条总结模型请求不得超过所选上限，包括重试请求。并发为 1 时总结请求仍串行，但允许与下一条内容补全重叠。
- 内容补全及其浏览器访问最多一条在途，保留原有访问预算、人工暂停和所有权规则。不能仅给现有整条 `_analyse` 包一层并发就同时启动多个浏览器会话。
- 先识别可复用总结与可用已存正文，避免可用条目排在外部补全后面等待。补全完成的输入先形成稳定可保存的输入记录，再进入总结；模型请求不得继续依赖会被下一条补全替换的浏览器会话状态。
- 条目领取、阶段转换和结果保存需要原子性，防止同一条目被多个消费者重复领取；数据库事务不跨网络等待。
- 完成顺序可以不同于选材顺序，但结果归属、引用身份与报告排序规则不随完成时序变化。成功结果逐条持久化，不等整批统一提交。
- 只有补全已结束、就绪队列无待处理项、所有在途与待重试工作已结算，才允许分析任务完成并触发一次报告汇总。补全暂时没有结果不能被误判为全批完成。

### 暂停、故障、取消与恢复

- 平台登录或安全验证只暂停继续补全；已经取得可用正文的条目允许继续总结并保存。父报告记录仍保持待人工处理，不提前汇总；继续操作沿用显式用户授权。
- 单条普通失败独立落库并继续其他条目；原帖文字不足按既有待人工核查逻辑处理。
- 模型鉴权、配置等系统性故障沿用现有配置阻断语义，并停止新请求；正确结算其他在途请求，禁止已结束父任务被晚到回调恢复运行。
- 取消和关闭必须停止生产及新请求派发，唤醒并结束等待队列或退避的消费者，清理所有归属的子任务、浏览器会话和 AI 租约。保留已持久化成功结果，不宣称能撤销服务商已经接收的请求或费用。
- 应用重启沿用中断恢复边界：不自动重发执行结果不明确的付费请求。历史并发快照、成功总结、失败诊断和使用量记录保留。

### 明确限流的有限重试

- 当前错误层将 HTTP 429 映射为“限流或额度不足”，不足以安全地一概重试。需保留脱敏、限长的状态码、服务商错误码和合法 `Retry-After` 等必要信息，区分短暂限流、余额或配额不足、以及不明确错误。
- 仅对明确短暂限流且尚未产生有效输出的请求启用该保护；额度耗尽、鉴权失败、普通超时、断流或结果不明确不因本次改造而自动重发。
- 优先遵守有效服务端等待提示，否则有界指数退避并加入抖动；任务级协调等待，避免 8 个消费者同步持续重试。无需在未发生限流时主动降低实际并发，也不承诺自动探测服务商额度。
- 重试次数和累计等待必须有明确有限预算；具体数值作为实现参数选择并由测试锁定，不宣称用户已确认某个数值。超过预算时按现有失败归类结算并给出可理解提示，不无限循环。
- 正在处理的计数以条目而不是网络尝试计数。各次可获得的使用量按既有规则记录，未知费用不能记为已确认零；重试不重复产生成功总结或多次汇总。
- 保留现有针对模型输出格式错误的有限修复策略，但不得与新增限流重试形成无界嵌套或突破在途上限。

## Testing Decisions

### 测试边界

- 建议以现有“生成报告”公开 API 到最终报告记录的集成测试为主边界：使用真实任务编排、临时 SQLite 和已有可替换模型／内容获取依赖，不为生产端、队列、worker 分别新增测试专用接口。
- 前端只增加必要的确认弹窗用户交互测试，沿用现有报告生成页及 API schema 测试方式。仅用 API 无法验证偏好记忆和用户看到的选择，因此这部分是必要补充。
- 这些测试边界是根据现有代码提出的方案，尚未获得用户单独确认；本轮遵循不继续访谈的要求完成规格发布，不将其标成已确认或已验收。
- 好测试关注外部可见行为：请求是否重叠、峰值是否受限、最终状态和来源是否正确、是否重复调用、是否正确保存。不要断言 worker 数量、内部队列类型、私有方法调用顺序或线程调度细节。

### 主要验收场景

1. 对 1、2、4、8、16 参数化测试：提供足够已就绪正文，用可控异步屏障阻塞模型回复，确认首波实际请求达到选定上限且后续不越界；并发 1 只有一个在途总结。
2. 使用 216 条合成来源测试默认 8：观察峰值不超过 8且能达到 8，全部来源恰好结算一次，无丢失、串源、重复总结或多份汇总。不用真实付费 API 或实际等候数分钟判定提速。
3. 用控制点证明第 1 条模型回复未完成时已开始第 2 条补全；同时阻塞获取依赖并确认补全峰值始终为 1。
4. 已存正文可在另一条外部补全等待时发起总结；复用已有可用总结不调用获取器或模型，所有已复用与新结果合计准确。
5. 模型乱序完成时，逐条持久化成功可通过公开记录读出，进度不超总数，报告归属与引用保持一致；最慢一条未结束时不得提前汇总。
6. 请求严格校验、缺省 8、任务快照读回、幂等重放、同 UUID 修改并发冲突，以及旧请求和历史串行任务迁移兼容。
7. 前端验证首次默认、每档选择、提交参数、重开与重启语义所需的偏好持久化、取消弹窗不记忆、损坏存储回退、待确认意图恢复以及运行中不可修改。
8. 明确 HTTP 429 短暂限流后有限重试成功，遵守服务端等待、不超过并发上限，并有用户可见提示；持续限流到预算上限后停止，不能无限重试。
9. 额度耗尽、401、普通超时、断流及已输出内容后的异常不被新增机制盲目重试；保留既有配置阻断与格式修复语义。
10. 某条普通失败不阻断其他成功条目；全部原帖文字不足仍能形成待人工核查报告，技术失败不伪装成无相关舆情。
11. 平台人工暂停期间已就绪正文继续总结，暂停状态不被并发完成回调覆盖；仅显式继续恢复补全，且最终只交接一次汇总。
12. 多个请求在途、生产端阻塞、队列等待及退避等待时分别取消；确认不再派发、清理完成、已保存成功保留，晚到结果不复活任务。
13. 应用关闭与重启不自动重发结果不明确的模型调用，不泄漏浏览器或 AI 所有权，不使排队任务永久饿死。
14. 两个报告生成任务及自动任务竞争时不因新增并发突破既有 AI 任务互斥，不因共享执行器让非目标入口意外使用默认 8。

### 既有先例与验证环境

- 复用现有报告生成测试中“复用三条总结并处理七条已存正文”、选材快照及重启不重发的集成夹具。
- 复用现有生成失败测试中的部分失败、配置故障阻断，以及取消测试中的外部边界屏障、并发取消和清理完成确认方式。
- 保留模型客户端、使用量核算、报告记录 schema 和迁移测试覆盖，必要时扩展已有低层测试，而不另建一套执行器测试框架。
- 所有开发、预览与验证在用户本机进行。默认用确定性替身，不访问真实平台、不使用聊天中公开的密钥、不产生付费调用；真实平台或付费性能验证须另行授权。

## Out of Scope

- 平台搜索并发、多个正文补全同时访问平台、解除浏览器所有权或登录安全边界。
- 同时生成多份报告、报告汇总或报告分节自身并发。
- 为自动任务新增并发配置界面或悄悄提高其默认并发。
- 运行中调整并发、自定义任意整数、跨设备偏好同步、自动基准测试和服务商额度管理。
- 全局分布式队列、远程服务部署、Centaurus 验证。
- 改换模型服务、让 LLM 直接读取原帖 URL、媒体分析和媒体缓存。
- 更改报告选材政策、关键词采集数量、相关性判定或提示词内容。
- 自动重跑历史内容或丢弃既有总结、报告、失败记录。
- 精确费用估算、固定倍数性能保证或本轮实际代码实施。

## Further Notes

- 配套规格：[舆情爬取界面的分平台访问间隔与限流暂停](../platform-access-pacing/spec.md)。用户要求两份规格后续一起实现：平台间隔首次均为 5 秒，在舆情爬取界面按平台保存，报告生成接纳时固定补全间隔快照；默认 8 的单条总结并发仍独立配置。共享任务快照、迁移、暂停、取消和等待预算须联合设计。
- 平台访问明确限流时暂停、保留进度并由用户显式继续，不适用本规格针对模型服务的有限重试。平台间隔等待或人工暂停不得阻塞已取得正文的并发总结；联合测试应覆盖这两个控制同时生效的情况。
