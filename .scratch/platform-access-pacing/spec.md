# 舆情爬取界面的分平台访问间隔与限流暂停

## Problem Statement

本机实测使用“龙田街道、龙田社区、老坑社区、竹坑社区、南布社区”五个纯地名搜索，不附加舆情词。小红书完成首词 10 条采集后，在第二个搜索词处再次暂停；使用者看到“请求太频繁”，后台却归类为需要安全验证，导致使用者无法判断应登录、验证还是等待。

现有串行搜索不等于低频访问：通用平台搜索路径在搜索词切换、翻页前缺少统一访问间隔，页面加载轮询不是限速措施。后续内容补全也需要遵守同平台访问节奏，否则搜索降速后仍可能因连续补全而触发限制。

使用者希望五个平台初始间隔统一为 5 秒，在舆情爬取界面分别配置并记忆；明确限流时暂停、保留进度，由使用者显式继续。此需求与单条总结默认 8 并发相互独立。

## Solution

在舆情爬取界面提供微博、抖音、快手、小红书、今日头条各自的“平台访问间隔（秒）”，初始均为 5 秒，可分别调整，保存最近配置。界面说明该间隔同时约束搜索词切换、翻页和报告生成中的原帖补全，不控制 LLM 单条总结并发。

采集批次、报告生成分别在启动时读取并固定所需平台间隔，后续配置变动不改变在途工作；等待间隔时保留可取消、可理解的进度反馈。五个平台共用限速机制，但各自计时、各自配置。

遇到明确平台限流，停止该平台的新自动访问，保持现有批次暂停边界并保留进度，显示“平台限流，请稍后再试”等有证据的原因；有平台等待提示时遵守，没有时不编造恢复时间。等待结束不自动继续，不用频繁刷新或重新登录代替冷却。已有正文的文字理解仍可继续。

## User Stories

1. As a 使用者, I want 在舆情爬取界面配置各平台访问间隔, so that 无需寻找单独设置页。
2. As a 首次使用者, I want 五个平台均默认 5 秒, so that 首次采集就有明确的访问节奏。
3. As a 使用者, I want 分别调整微博、抖音、快手、小红书和今日头条的间隔, so that 不同平台可以采用不同速度。
4. As a 使用者, I want 最近配置被本地保存并在重新打开应用后恢复, so that 不必每次重复设置。
5. As a 使用者, I want 清楚看到秒数单位与生效范围, so that 不把间隔误解为每条总结耗时。
6. As a 使用者, I want 不合法的间隔在提交前被指出, so that 不会用零间隔或错误类型启动任务。
7. As a 使用者, I want 设置变化仅影响之后启动的任务, so that 在途采集不会忽快忽慢。
8. As a 使用者, I want 报告生成也固定启动时的平台间隔, so that 之后修改采集配置不会改变该报告的补全节奏。
9. As a 使用者, I want 搜索词切换遵守访问间隔, so that 第一词完成后不会立刻连续请求第二词。
10. As a 使用者, I want 翻页遵守同平台访问间隔, so that 同一搜索词也不会快速连续加载多页。
11. As a 使用者, I want 内容补全遵守同平台访问间隔, so that 搜索阶段的降速不会被详情访问抵消。
12. As a 使用者, I want 同平台在不同任务和阶段间延续访问节奏, so that 切换任务不能绕过刚发生的访问间隔。
13. As a 使用者, I want 平台访问与模型总结并发独立, so that 访问变慢时已取得正文的内容仍可并发理解。
14. As a 使用者, I want 复用已有正文或可用单条总结不产生不必要访问, so that 不为没有网络请求的步骤额外等待。
15. As a 使用者, I want 访问等待具有清楚状态且可以取消, so that 不误以为系统卡住或已中断。
16. As a 使用者, I want 明确限流与登录失效、安全验证分别说明, so that 知道是稍后再试还是需要操作账号。
17. As a 使用者, I want 请求频繁后暂停并保存已采集结果, so that 不丢失前面完成的关键词进度。
18. As a 使用者, I want 平台给出等待要求时应用遵守, so that 不在冷却期间继续请求。
19. As a 使用者, I want 平台没有给恢复时间时应用如实说明, so that 不被虚构的倒计时误导。
20. As a 使用者, I want 冷却结束后仍由我显式继续, so that 不会突然恢复自动访问。
21. As a 使用者, I want 继续采集不重跑已完成关键词, so that 不增加重复访问压力。
22. As a 使用者, I want 暂停时已取得正文仍可形成单条总结, so that 平台等待不会整体停用文字理解。
23. As a 使用者, I want 连续点击继续或重启应用不能清除已知冷却要求, so that 不会意外造成密集重试。
24. As a 使用者, I want 取消或关闭能及时结束间隔等待并释放资源, so that 不用等待全部计时结束才能退出。
25. As a 使用者, I want 历史任务与已完成报告继续可读, so that 新配置不破坏原有资料。
26. As a 使用者, I want 知道 5 秒不是平台承诺的安全阈值, so that 不误以为设置后绝不会限流。
27. As a 使用者, I want 自动入口也不绕过平台访问限制, so that 手动设置不是只对一个按钮有效。
28. As a 维护者, I want 保留脱敏的限流证据及发生阶段, so that 排查时不只看到含糊的“已中断”。

## Implementation Decisions

### 产品配置与快照

- 在舆情爬取界面增加五个平台的间隔编辑及明确保存反馈，不移到设置页或报告生成确认界面。该配置是本机应用级偏好，不是关键词、监控规则或采集条数限制。
- 偏好由后端本地持久化并通过公开 API 读写，便于报告生成及自动入口取得同一配置；不只保存在某个前端页面内存中。
- 初始值五个平台均为 5 秒。实现细化建议使用 1～300 的整数秒，拒绝布尔值、非整数、非有限值及范围外数值，禁止 0 关闭限速；具体输入范围不是用户逐项指定的数值，但必须前后端一致并有测试。
- 只有成功保存的完整配置成为新任务默认值；非法或存储失败的更新不部分生效，界面不得显示保存成功。任务进行时可保存后续任务的偏好，并提示不改变当前任务。
- 采集批次与报告生成在持久化接纳时固定所需平台间隔；排队、恢复、报告内部延迟开始补全时均用该快照，不能届时重读偏好。未显式创建父报告的既有分析入口也需固定自己的补全快照。
- 前端请求重放必须保持既有幂等语义。对报告创建，应先识别已存在意图再读取当前偏好；相同 UUID 重放不能因偏好已变化覆盖历史快照或产生新任务。
- 返回记录中能读出实际平台间隔快照。旧记录缺少快照时显式按兼容规则解释，不能声称历史曾采用 5 秒；升级后恢复需执行网络访问的旧任务使用一次性确定并保存的安全缺省，保持旧报告和成功结果不变。
- 自动任务没有新增独立配置界面，但使用相同应用级平台间隔，并在其阶段任务接纳时固定，不能成为限速旁路。不改变自动触发条件或选材政策。

### 统一访问节奏

- 为应用主动发起的平台内容访问提供一个可复用的协调机制；搜索和补全不各自实现互不相干的 sleep。按平台独立记录最近一次访问开始时间，同一平台跨任务和阶段共享访问历史。
- 访问间隔定义为同平台相邻受控访问开始时间的最小间隔。请求或页面加载本身超过间隔时，无需再无条件等待一个完整间隔；首次访问无历史且无冷却限制时可以立即执行。
- 覆盖搜索词切换、翻页、重新导航等会触发新的内容访问的操作，以及原帖补全的实际受控内容请求。获取器内部能由现有请求桥接控制的内容请求也需遵守约束，不能只在外层每条补全前等待。
- 切换最新排序、滚动加载等若触发额外内容访问，也应纳入应用可控制的触发边界，不因没有传统翻页 URL 被漏掉。
- 仅本地读取 DOM、处理已取得数据、读取数据库和调用 LLM 不属于平台访问。浏览器加载的每个样式、脚本、认证资源不逐个强制间隔，也不恢复资源拦截；不承诺精确控制浏览器全部底层网络请求。
- 用户主动登录、验证码操作和平台账号页面正常加载继续遵守既有人工操作例外，不接管或阻断用户浏览器交互；但应用不能借账号检查自动反复探测限流恢复。
- 同平台连续任务使用不同快照时，新的请求同时遵守当前任务间隔、上一请求留下的最早允许时间及已知平台冷却，以较晚时间为准，避免较短新配置立即突破旧约束。
- 间隔等待可取消、非阻塞事件循环，不持有 SQLite 事务。保留原有浏览器互斥和串行内容补全，不因加入协调器开放多个平台浏览器同时操作。
- 任务的主动访问预算与正常限速等待需区分：等待不耗掉尚未发出的单次网络请求超时；整体工作仍需有界。实施时调整或单独核算主动等待预算，避免五词十页的合法配置仅因新增 sleep 被统一短时限提前判超时；不能简单取消所有总预算。

### 限流识别、暂停与恢复

- 在搜索与原帖补全的统一错误边界识别明确 HTTP 限流状态、平台错误码或可信页面障碍中的“请求太频繁”等提示；登录、安全验证、访问拒绝和限流应有可区分原因。
- 现有某些分类先匹配安全验证、再匹配限流，需要结合可信障碍区域检查优先级及组合情况。若明确限流同时包含验证要求，至少保留限流原因，并补充人工验证要求，不能笼统引导重新登录。
- 不把原帖正文中的“请求频繁”“验证码”等普通讨论当作障碍，不把泛泛“稍后再试”或普通 403 无证据地断言为频率限制。
- 记录脱敏、限长的错误码、阶段、平台和必要证据；界面从实际原因显示提示，不由前端根据一个宽泛终态猜测。没有足够证据时如实标记未知或访问失败。
- 明确平台限流后暂停，不自动有限重试或自动轮询恢复。本规则与模型服务限流不同：模型限流保护仍按单条总结并发规格执行。
- 保持既有批次暂停边界：当前平台遇阻时整个采集批次暂停，后续平台不自动绕过去运行。仅使用已有正文的文字理解可继续，符合既有 ADR；本次不引入平台独立后台继续采集。
- 有可信 `Retry-After` 或平台等待要求时保存最早允许恢复时间；显式继续也不能提前发出新内容请求。无等待时间时不编造冷却结束时间；使用者可稍后显式继续，新的访问仍受固定间隔约束。
- 继续操作创建或恢复既有检查点流程，不重跑已确认完成的关键词；若仍受限则再次暂停，不在同次继续内部循环重试。
- 保存的冷却约束不因切换任务、连续点击继续或应用重启而清空。重启后仍保持暂停且不自动访问，运行中用单调时间计时，持久化时间需处理时钟变化，避免负等待或忙循环。
- 取消、关闭、配置故障和所有权释放沿用现有结算规则，等待中的任务能及时停止；本次不擅自清理历史数据或恢复当前暂停批次。

### 与单条总结并发的共同实施

- 两个功能使用同一条流水线边界：串行且受间隔控制的内容补全 → 有界就绪队列 → 默认最多 8 条并发文字理解 → 条目结算后报告汇总。
- 平台间隔在舆情爬取界面配置；单条总结并发数在生成报告确认界面选择，两者快照分别保存，不能共用一个“速度”参数。
- 一个任务持有稳定 AI 配置租约，平台访问协调器不延迟已就绪正文的 LLM 请求。人工暂停期间已取得正文的总结继续执行，且不得提前汇总仍有待恢复补全的报告。
- 共享的任务快照、迁移、暂停投影、取消和等待预算应合并设计与验证，避免两个功能各自修改同一流程产生双重等待、双重迁移或相互覆盖。

## Testing Decisions

### 主要测试边界

- 优先使用现有采集批次和报告生成的公开 API 集成边界，贯穿真实编排、临时 SQLite、可替换浏览器／获取器与模型依赖。它们是两个既有业务入口，不为每个计时器或 worker 新建测试接口。
- 对时间引入最小必要的可控时钟／等待依赖，在外部访问替身记录访问时刻和重叠情况；它是测试控制手段，不以内部 sleep 次数或私有队列实现作为验收对象。
- 补充现有舆情爬取页面交互测试，验证配置位置、默认值、逐平台编辑、保存反馈、非法输入、任务进行时的说明及重新打开后的恢复。
- 测试边界是基于现有代码的建议，用户未逐项确认；本轮按不继续访谈的要求发布规格，不声称已验收。

### 验收覆盖

1. 新数据库五个平台默认 5 秒；设置 API 原子保存、读回及应用重开恢复，非法字段、整数边界和存储失败不会部分生效。
2. 保存 A 配置创建采集／报告任务，再保存 B：已有任务继续用 A，新任务用 B；排队任务、暂停后继续和相同报告 UUID 重放均不变。
3. 搜索词切换、翻页、会触发新内容访问的排序及补全请求间隔符合快照；同平台跨阶段不绕过，异平台历史不会无故拖慢彼此。
4. 页面加载已超过间隔不重复多等完整间隔；纯 DOM 读取、已有正文和总结复用不产生平台访问或无意义延时。
5. 获取器内部受控内容请求也遵守间隔；网页认证资源正常加载不被重新拦截，人工登录不受自动限速器错误阻断。
6. 使用虚拟时钟覆盖长间隔、多词多页，确认主动等待不被误报成网络超时，同时总工作预算仍有限。
7. 构造小红书可信“请求太频繁”障碍，验证原因不是单纯要求登录；限流加验证保留两类必要提示；正文提及相同词语不误判。
8. 验证明确 HTTP 限流、有无恢复时间、普通 403、泛化错误提示的分类与脱敏投影，不能把未知原因编成确定限流。
9. 平台限流后整批暂停、后续平台不访问；首词已保存十条仍保留，显式继续从未完成词恢复，不自动重试或轮询。
10. 有冷却截止时提前继续不得访问；截止过去也不自动继续；重启和新任务不能绕过已知限制。
11. 补全等待／限流暂停时，已就绪的 8 条总结可以并发运行；平台实际补全仍串行，正常间隔等待不显示“已中断”。
12. 在间隔等待、冷却等待、在途访问及模型总结阶段取消，确认不再派发新访问，资源清理完成、已保存结果保留、晚到回调不复活任务。
13. 历史数据库升级、旧任务快照兼容、自动入口固定间隔与报告幂等重放不产生重复请求。
14. 端到端合成 216 条来源，在默认平台 5 秒和默认总结 8 并发条件下，使用可控时间证明平台节奏、模型峰值、正确来源归属和唯一汇总共同成立，不以真实等待时长作断言。

### 既有先例与运行环境

- 复用采集批次测试的人工验证暂停、继续生成新尝试、规则快照、取消停止后续平台、重启不自动恢复等场景。
- 复用原生平台发现测试的障碍页面与请求替身，以及内容补全的请求预算、浏览器所有权和状态映射测试。
- 复用报告生成取消测试中的异步屏障、外部清理确认，以及舆情爬取界面的批次恢复交互测试。
- 本地验证为默认且唯一授权环境，优先确定性替身；真实平台访问和付费模型测试另外获得授权，不接入 Centaurus，不复用聊天中公开的密钥。

## Out of Scope

- 保证 5 秒不会限流、推断平台隐藏阈值、自动提速或绕过验证码、账号限制及风控。
- 自动轮询平台恢复、冷却结束自动继续、当前平台暂停后偷偷运行同批次其他平台。
- 对浏览器每个资源请求逐个限速或重新启用认证资源拦截。
- 改变关键词、每词采集上限、报告选材、相关性规则或原帖文字分析范围。
- 修改 LLM 总结并发选项、把平台限流当作模型限流自动重试。
- 跨设备配置同步、远程采集、Windows 中断原因的无证据归因。
- 本轮实施代码、恢复当前批次或再次发起真实平台请求。

## Further Notes

- 已确认：五个平台初始统一 5 秒、可分别调整、放在舆情爬取界面、记忆配置、采集与报告分别在启动时固定、限流暂停后显式继续、与总结并发独立。
- 本机批次曾在小红书首词取得 10 条后于第二词暂停，后台记录需要安全验证，使用者反馈页面提示请求太频繁。这是改进访问节奏和原因展示的依据，不是已证实 Windows“已中断”的根因。
