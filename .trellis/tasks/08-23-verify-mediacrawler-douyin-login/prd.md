# 验证 MediaCrawler 抖音登录与登录态持久化

## Goal

验证 MediaCrawler 在独立 Chrome 中能否完成抖音首次扫码登录，并在浏览器完全退出后复用有效登录态；若原生 profile 不能稳定复用，则最小接入现有 `BrowserAuthStateStore`，为后续本地单用户舆情工具提供可重复使用的抖音平台连接能力。

## Background

- 当前抖音 crawler 使用 `https://www.douyin.com`，登录类型支持二维码、手机号和 Cookie；本任务只使用二维码。
- `DouYinClient.pong()` 通过页面 LocalStorage 的 `HasUserLogin == "1"` 或浏览器 Cookie 的 `LOGIN_STATUS == "1"` 判断当前登录状态。
- 现有流程在登录后只更新内存 client Cookie，没有显式调用通用 `BrowserAuthStateStore`，也没有再次执行 `pong()`。
- CDP 模式在 `SAVE_LOGIN_STATE=True` 时已有独立 Chrome profile，但它是否足以跨进程复用抖音状态必须用真实两次启动验证。
- 微博和快手任务已经建立通用认证状态存储、安全日志、`0600` 权限和两次启动验收基线。
- 抖音现有 `DouYinLogin` 会在检测到滑块验证时识别缺口并自动拖动；源码同时注明该机制准确率不高。这与项目现行“不得自动绕过平台安全验证”的认证规范冲突。

## Requirements

- 使用 `dy`、`qrcode`、可见的独立 Chrome 和任务专用临时用户数据目录，不连接日常 Chrome。
- 使用不会进入 search/detail/creator 的认证验证模式，不采集作品、评论或用户信息。
- 在任何真实运行前，将抖音滑块路径改为只检测、提示并等待用户手工完成；不得识别缺口、模拟拖动、自动刷新或重试绕过。
- 先验证原生首次扫码和浏览器完全退出后的第二次启动，不预设一定需要修改持久化逻辑。
- 若原生第二次启动仍要求扫码，在同一任务内最小复用 `BrowserAuthStateStore`，使用抖音现有 URL allowlist，恢复必须早于 client 创建和首次 `pong()`。
- 登录完成后更新 client，并再次通过登录状态检查后才允许保存认证状态；`SAVE_LOGIN_STATE=False` 时不读写认证状态。
- 登录状态、浏览器 profile 和运行证据不得进入 Git；日志只记录结果、顺序、数量和文件元数据，不记录 Cookie 名称、值、二维码内容或认证请求头。
- 真实验证结束后关闭 Chrome/CDP，删除本任务创建且包含真实登录态的临时目录；不覆盖或删除现有 `browser_data/`、`db_data/`、`logs/`。

## Acceptance Criteria

- [x] 独立 Chrome 和抖音登录页正常打开，二维码可见，用户扫码后登录流程确认成功。
- [x] 认证验证模式正常结束，且没有进入任何内容采集分支。
- [x] 完全关闭 Chrome 后第二次启动无需再次扫码；原生 profile 已通过，因此无需条件接线。
- [x] 本轮未发生条件接线；持久化编排测试不适用。
- [x] 平台安全验证未被自动绕过；活动自动识别、拖动、刷新和重试路径已移除并由测试覆盖。
- [x] 临时配置恢复，Chrome/CDP 退出，端口关闭，敏感临时目录删除，源码变更保持在批准范围内。

## Out of Scope

- 抖音关键词搜索、作品详情、评论、下载和长期采集稳定性。
- 抖音开放平台 OAuth/API 接入。
- React/FastAPI 平台连接页面。
- 今日头条、小红书或其他平台。
- 登录态加密、系统钥匙串和多账号管理。

## Key Decisions

- 用户已确认平台滑块只允许人工处理。滑块不一定每次出现；不出现时继续正常二维码流程，出现时在可见的独立浏览器中等待人工完成，超时则安全结束本轮。
- 先保留抖音现有 `pong()` 作为本任务的登录状态合同，并通过“第二次启动首次检查通过且不出现二维码”的真实回归验证其可用性；本任务不引入内容 API 请求作为额外探针。
- 任务保持单任务结构：安全修正、原生基线和条件式持久化属于同一条可独立验收的抖音认证链路，不拆分子任务。
