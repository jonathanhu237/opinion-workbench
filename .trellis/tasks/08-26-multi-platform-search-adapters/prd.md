# 多平台搜索适配

## Goal

在已经跑通的今日头条手动采集链路上，逐个平台增加微博、快手、抖音和小红书搜索，最终让用户可以针对同一条监控规则选择不同平台执行搜索，并继续获得可追溯、可去重的原文结果。

## Background

- 今日头条已经证明了“监控规则 → 借用用户谷歌浏览器 → 平台搜索 → FastAPI 持久化 → React 展示”的完整链路。
- 五个平台的账号检测均已有独立实现，但账号检测通过不等于关键词搜索已经具备产品级可用性。
- 现有能力审计建议按风险和成熟度依次适配：微博、快手、抖音、小红书。
- 四个平台的搜索机制、登录要求、风控表现和结果结构不同，需要分别规划、实测和验收。

## Requirements

- 父任务维护四个平台的共同目标、适配顺序、跨平台兼容性和最终集成验收，不直接承载四个平台的混合实现。
- 每个平台使用独立子任务完成需求确认、技术设计、实现、检查和真实浏览器验收。
- 新平台复用现有监控规则、搜索任务、结果历史和全局去重能力，不另建一套平行业务流程。
- 平台失败不得影响已有今日头条链路，也不得被表示成成功但无结果。
- 所有平台继续使用用户已经批准的常驻谷歌浏览器连接；平台操作保持全局串行，并且只关闭任务自己创建的页面。
- 登录、短信、滑块或安全验证由用户在可见浏览器中人工完成，不自动绕过。
- FastAPI 继续拥有运行状态、规范化结果和产品 SQLite；MediaCrawler 只负责平台适配与受限事件输出。
- 平台内部响应、Cookie、LocalStorage、认证头、浏览器数据目录和原始异常不得暴露给前端或进入不受控日志。

## Acceptance Criteria

- [ ] 微博、快手、抖音和小红书均有独立子任务及可审计的适配结论。
- [ ] 每个已完成平台都能在现有采集任务页面中被真实选择和执行，并复用同一套运行历史、结果详情、来源词和新旧内容判断。
- [ ] 同一平台内容重复命中时继续按 `(platform, platform_content_id)` 全局去重；不同平台之间不会误合并。
- [ ] 每个平台的空结果、登录要求、人工验证、访问限制、页面或协议变化、取消和内部故障都有真实且可操作的状态。
- [ ] 四个平台的增量适配不会破坏今日头条搜索、平台账号检测、监控规则或既有数据库数据。
- [ ] 每个平台在声明完成前均通过离线测试和一次用户可见的真实浏览器验收。

## Out of Scope

- 定时执行、自动重试、断点续跑和历史回填。
- AI 情绪判断、风险分级、摘要、告警、日报和处置流程。
- 评论、用户主页、媒体下载、账号池以及验证码或滑块绕过。
- 在一个子任务里同时改动或实测多个新平台。
