# MediaCrawler 运行时依赖评估

## 问题

在项目已决定使用 React + FastAPI、复用用户当前 Chrome Profile 的前提下，判断
MediaCrawler 是否仍应作为产品运行时的核心采集引擎。

该决策不阻塞当前前后端初始化；初始化任务应保持采集实现中立。

## MediaCrawler 提供的现成价值

- 多平台搜索、详情、创作者和评论采集实现。
- Playwright/CDP 浏览器连接、登录流程、平台客户端、结果解析和多种存储后端。
- 小红书、抖音、快手、微博等平台已有 CDP 路径；派生仓库已补充今日头条和多平台
  登录态相关改动。
- 已有 CLI、FastAPI WebUI API 和子进程管理代码，能够作为外部采集进程运行。

## 与本产品的差距

- 当前产品的核心需求是按关键词和地址发现公开内容、返回原始链接、去重、定时执行、
  AI 分析和任务闭环；MediaCrawler 主要负责采集本身，不提供完整舆情业务闭环。
- MediaCrawler 使用全局 `config`、CLI 参数和平台 store，直接导入产品 FastAPI 进程
  容易造成配置污染和生命周期耦合。
- 其 WebUI API 使用全局单例管理单个子进程，状态和日志主要在内存中，不适合作为
  产品数据库和任务模型。
- 派生仓库的 WebUI API 平台枚举尚未包含今日头条，说明爬虫核心和 UI/API 仍需同步
  维护。
- 本产品第一阶段只需要搜索结果链接，MediaCrawler 的评论、媒体下载、代理池和多种
  存储能力超出当前范围。

## 许可证风险

`NON-COMMERCIAL LEARNING LICENSE 1.1` 授权范围是“非商业学习目的”，并明确限制为
“学习和研究用途”。不收费或非营利不必然等同于学习研究。面向街道实际运行的舆情
系统可能超出许可范围，需要版权所有者书面确认；Fork 不会改变上游代码许可证。

该判断是工程风险提示，不代替正式法律意见。

## 可选方案

### A. MediaCrawler 作为运行时引擎

- 优点：最快复用多平台能力，已有派生适配投入可继续使用。
- 实施方式：产品 FastAPI 通过受控子进程调用，不直接 import 到主服务；产品负责
  参数、任务、结果归一化和 SQLite，MediaCrawler 只负责平台采集。
- 前提：确认使用场景符合许可证，或取得版权所有者书面许可。

### B. 复制部分代码进入 backend

- 不推荐。复制代码仍受原许可证约束，同时失去 submodule 的边界和上游同步能力。

### C. 项目自建轻量采集适配器

- 只实现五个平台的搜索页/CDP 适配，输出统一的标题、链接、作者、发布时间和摘要。
- 优点：架构更小、完全符合产品数据模型、无 MediaCrawler 代码许可证耦合。
- 缺点：平台页面和接口变化需要自行维护，长期成本显著；若未来采评论和详情，成本
  会继续增长。
- 自建实现仍需遵守平台条款、数据与隐私相关法律要求。

### D. 使用平台官方接口或取得授权的数据服务

- 合规和稳定性潜力最高，但国内平台公开搜索能力、覆盖范围和费用需另行验证。

## 已确认决策（2026-08-24）

1. 保留现有 `third_party/MediaCrawler` submodule 和派生改动，不删除、不复制代码。
2. 后续选择 A，将 MediaCrawler 作为平台采集引擎；用户确认该项目为非商业用途，
   不计划另行申请书面授权，并接受已记录的许可证适用性风险提示。
3. 产品 FastAPI 通过受控子进程调用 MediaCrawler，不直接 import 到主服务，也不
   复用其 WebUI API 作为产品后端。
4. 产品后端拥有任务状态、调度、SQLite 数据、结果归一化、去重和舆情业务流程；
   MediaCrawler 只拥有浏览器连接及平台采集。
5. 当前 React + FastAPI 初始化仍不启动或封装 MediaCrawler，只为未来集成保留清晰
   目录边界。
